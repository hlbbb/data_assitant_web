# Agent 开发编码规范

## 1. 沟通与思考语言
全程使用中文进行逻辑思考、问题沟通及文档编写,确保协作清晰无歧义。

## 2. 工具使用规范

### 2.1 思考工具
学会使用思考系列工具来解决复杂问题:
- 遇到复杂逻辑时,先使用思考工具梳理思路
- 多步骤任务前,先规划再执行
- 遇到报错时,先分析根因再修复

### 2.2 代码索引 MCP (重要)
**写代码前必须使用代码索引MCP工具**:
- 查找相关函数、类、变量的定义位置
- 了解代码的调用关系和依赖链路
- 查看相关模块的实现方式
- 避免重复造轮子,复用已有代码

使用场景:
```
- 修改某个函数前 → 先索引该函数的所有调用位置
- 新增功能前 → 先索引相关模块的实现方式
- 重构代码前 → 先索引影响范围
- 修复Bug前 → 先索引相关代码的上下文
```

### 2.3 其他工具
- **Glob**: 快速查找文件
- **Grep**: 搜索代码内容
- **Read**: 阅读文件内容
- **Edit**: 编辑文件(优先于直接写入)

## 3. 技能(Skills)使用规范

学会使用不同技能解决不同问题:

| 问题类型 | 推荐技能 | 说明 |
|---------|---------|------|
| 前端开发 | `frontend-designer-skill` | UI设计、组件开发 |
| 后端开发 | `backend-patterns` | API设计、架构模式 |
| 数据库 | `postgres-patterns` / `clickhouse-io` | 查询优化、Schema设计 |
| 安全问题 | `security-reviewer` | 安全审计、漏洞检测 |
| 代码审查 | `code-reviewer` | 代码质量检查 |
| 测试开发 | `tdd-guide` | 测试驱动开发 |
| Go项目 | `golang-patterns` / `go-review` | Go语言最佳实践 |
| Python项目 | `python-patterns` / `python-review` | Python最佳实践 |
| 文档编写 | `doc-updater` | 文档更新维护 |

## 4. 代码修改规范

### 4.1 修改前准备
- **明确目的**: 清楚为什么要修改,预期效果是什么
- **评估影响**: 分析修改会影响哪些模块、功能、用户
- **查阅文档**: 查看项目架构设计、模块说明
- **索引代码**: 使用代码索引MCP了解上下游关联

### 4.2 修改原则
- ❌ **禁止盲目改动**: 不理解代码逻辑不修改
- ❌ **禁止局部修改**: 必须考虑上下游关联逻辑
- ❌ **禁止破坏性修改**: 避免引发整体程序崩溃
- ✅ **渐进式修改**: 小步快跑,逐步验证
- ✅ **保持一致性**: 遵循项目现有代码风格

### 4.3 修改后验证
- 进行基础自测,验证核心功能正常
- 检查是否影响其他模块
- 运行相关测试用例
- 检查是否有编译错误、类型错误

## 5. 前置查阅要求

执行代码修改前,必须完成以下查阅:

### 5.1 项目文档
- [ ] 项目整体架构设计文档
- [ ] 模块说明文档
- [ ] API文档(如有)
- [ ] 数据库设计文档(如有)

### 5.2 代码历史
使用git工具查看:
```bash
# 查看文件修改历史
git log --follow <file_path>

# 查看某次提交的详细变更
git show <commit_hash>

# 查看文件的 blame 信息
git blame <file_path>

# 查看分支结构
git branch -a
```

### 5.3 代码索引
使用代码索引MCP:
- 查找相关函数定义
- 查找所有调用位置
- 查找相关类/接口
- 查找配置项使用位置

## 6. Git 提交规范

### 6.1 提交语言
- **提交信息使用英文**
- 代码注释根据项目约定(通常中文)

### 6.2 提交格式
保持与项目现有提交格式一致,通常遵循 Conventional Commits:

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type类型**:
- `feat`: 新功能
- `fix`: Bug修复
- `refactor`: 重构
- `docs`: 文档更新
- `test`: 测试相关
- `chore`: 构建/工具相关
- `perf`: 性能优化
- `style`: 代码格式调整

**示例**:
```
feat(auth): add JWT token refresh mechanism

- Add refresh token endpoint
- Implement automatic token refresh in client
- Add token expiration validation

Closes #123
```

### 6.3 提交前检查
- [ ] 代码已自测
- [ ] 无编译错误
- [ ] 无明显Bug
- [ ] 提交信息格式正确
- [ ] 提交粒度合理(一个提交解决一个问题)

## 7. 代码审查规范

### 7.1 审查时机
**写完代码后必须启动审查**:

```bash
# 审查特定文件
opencode run "审查 src/auth/login.ts 的改动"

# 审查某个功能
opencode run "审查用户登录功能的实现"

# 审查某次提交
opencode run "审查 commit abc123 的改动"
```

### 7.2 审查重点
- 代码逻辑是否正确
- 是否有安全漏洞
- 是否有性能问题
- 是否符合项目规范
- 是否有更好的实现方式
- 是否有遗漏的边界情况

### 7.3 审查后处理
- 根据审查意见修改代码
- 修改后再次审查
- 审查通过后再提交
- 提交时注明已通过审查

## 8. 开发流程总结

```
1. 接收任务
   ↓
2. 理解需求(中文思考沟通)
   ↓
3. 查阅文档 + 代码索引MCP
   ↓
4. 使用合适技能(如 frontend-designer-skill)
   ↓
5. 编写/修改代码
   ↓
6. 自测验证
   ↓
7. 启动审查(opencode run)
   ↓
8. 根据审查意见修改
   ↓
9. 提交代码(英文,规范格式)
   ↓
10. 完成
```

## 9. 常见问题处理

### 9.1 遇到报错
1. 不要立即修改代码
2. 使用思考工具分析根因
3. 使用代码索引MCP查找相关代码
4. 查阅文档了解正确用法
5. 制定修复方案
6. 小步修改并验证

### 9.2 需要新增功能
1. 先索引类似功能的实现
2. 查阅项目架构文档
3. 使用相关技能(如 frontend-designer-skill)
4. 参考现有代码风格
5. 编写代码并测试
6. 启动审查

### 9.3 需要重构代码
1. 使用代码索引MCP了解影响范围
2. 查看git历史了解演进过程
3. 评估重构风险
4. 制定重构计划
5. 小步重构,逐步验证
6. 启动审查

## 10. 最佳实践

### 10.1 代码质量
- 保持函数简短(<50行)
- 保持文件聚焦(<800行)
- 避免深层嵌套(<4层)
- 使用有意义的命名
- 添加必要的注释

### 10.2 安全意识
- 不硬编码敏感信息
- 验证所有用户输入
- 使用参数化查询
- 启用CSRF保护
- 错误信息不泄露敏感数据

### 10.3 性能考虑
- 避免N+1查询
- 合理使用缓存
- 异步处理耗时操作
- 优化数据库索引
- 减少不必要的网络请求

---

**记住核心原则**:
1. 写代码前先索引(代码索引MCP)
2. 修改前先理解(查阅文档+历史)
3. 写完后要审查(opencode run)
4. 提交时要规范(英文+格式一致)
