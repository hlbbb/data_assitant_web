# 第三阶段：多表连接

> 这一阶段咱们聊多表连接。数据库里的数据散落在不同表里，想把它们串起来，就得用连接。别怕，我用大白话带你走一遍。

---

## 先想清楚：什么时候需要JOIN？

很多新手一上来就JOIN，其实很多时候根本不需要。先问自己几个问题：

**需要JOIN的典型场景：**
- 查员工信息，同时要显示部门名称（员工表只有dept_id，部门名称在另一张表）
- 订单列表要显示用户名、商品名（订单表只存了user_id和product_id）
- 统计每个部门的业绩（部门表+订单表关联）
- 找出没有订单的用户（用户表LEFT JOIN订单表，筛NULL）

**不需要JOIN的情况：**
- 单表查询就能搞定的事，别硬JOIN
- 数据已经在应用层缓存了，直接用缓存
- 只需要ID列表，不需要关联表的字段

**JOIN选择决策树（文字版）：**

```
开始
  │
  ├─ 两边数据都要匹配上？
  │     └─ 是 → INNER JOIN
  │
  ├─ 左边数据必须全保留？
  │     └─ 是 → LEFT JOIN
  │
  ├─ 右边数据必须全保留？
  │     └─ 是 → RIGHT JOIN
  │
  ├─ 两边数据都要保留？
  │     └─ 是 → FULL OUTER JOIN（MySQL用UNION模拟）
  │
  ├─ 需要所有排列组合？
  │     └─ 是 → CROSS JOIN（慎用！）
  │
  └─ 同一张表自己跟自己比？
        └─ 是 → SELF JOIN
```

## 1. INNER JOIN 内连接

内连接就是拼表——两张表按条件粘在一起，只保留两边都能匹配上的行。

**生活比喻**：两个人必须都到场才能开会。你来了，对方没来，这场会就不算。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的 | `INNER JOIN ... ON` | 标准写法，连接条件和过滤条件分得清 |
| 不好 | `FROM 表A, 表B WHERE 表A.键 = 表B.键` | 老式隐式连接，连接和过滤混在一起，容易出bug |

**案例1（基础）**：查询员工及所属部门

```sql
-- 只有能匹配上部门的员工才会出现
-- 孙浩（无部门）和郑雪（部门不存在）不会出现
SELECT
    e.name      AS 员工姓名,
    e.salary    AS 薪资,
    d.dept_name AS 部门名称
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;
```
**运行结果：**

```text
+----------+----------+------------+
| 员工姓名 | 薪资     | 部门名称   |
+----------+----------+------------+
| 张伟     | 25000.00 | 技术部     |
| 李娜     | 18000.00 | 技术部     |
| 王强     | 16000.00 | 技术部     |
| 赵敏     | 20000.00 | 市场部     |
| 刘洋     | 15000.00 | 市场部     |
| 陈静     | 17000.00 | 财务部     |
| 周磊     | 14000.00 | 财务部     |
| 吴芳     | 13000.00 | 人事部     |
+----------+----------+------------+
共8条
```


**案例2（进阶）**：多表内连接 + 聚合

```sql
-- 每个部门的员工人数和平均薪资
SELECT
    d.dept_name             AS 部门名称,
    COUNT(*)                AS 员工人数,
    ROUND(AVG(e.salary), 2) AS 平均薪资
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id
GROUP BY d.dept_name
ORDER BY 平均薪资 DESC;
```
**运行结果：**

```text
+----------+----------+----------+
| 部门名称 | 员工人数 | 平均薪资  |
+----------+----------+----------+
| 技术部   |        3 | 19666.67 |
| 市场部   |        2 | 17500.00 |
| 财务部   |        2 | 15500.00 |
| 人事部   |        1 | 13000.00 |
+----------+----------+----------+
```


**教学点 #1**：INNER JOIN 只留匹配行，像筛子一样，两边都对上才通过。

**可视化理解（Venn图效果）**：
想象两个圆圈，左边是员工表，右边是部门表。INNER JOIN就是取两个圆的**交集**——只有两边都有的部分才保留。孙浩（无部门）在左圆外侧，运营部（无员工）在右圆外侧，都被切掉了。

### 真实业务案例：用户订单关联查询

这是最常见的JOIN场景。假设你有用户表和订单表：

```sql
-- 查询有下单记录的用户及其订单金额
SELECT
    u.username    AS 用户名,
    u.phone       AS 手机号,
    o.order_no    AS 订单号,
    o.amount      AS 订单金额,
    o.create_time AS 下单时间
FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE o.create_time >= '2024-01-01'
ORDER BY o.amount DESC
LIMIT 20;
```

**业务场景**：运营要看"最近下单的大客户名单"，用于精准营销。

---

### 新手常见坑

**坑1：以为INNER JOIN会保留所有数据**
错！INNER JOIN是"严格匹配"，两边都对上才保留。想保留所有员工？用LEFT JOIN。

**坑2：多表JOIN时忘记关联条件**
```sql
-- 错误写法：漏了关联条件，变成笛卡尔积
SELECT * FROM employees, departments;

-- 正确写法：必须指定关联条件
SELECT * FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;
```

**坑3：JOIN太多表导致性能爆炸**
一张表JOIN 5张以上，查询速度会明显下降。建议：
- 先在应用层拆分查询
- 或者用冗余字段减少JOIN（比如订单表直接存用户名，不存user_id）

---

### 面试高频题

**Q：INNER JOIN和LEFT JOIN的区别？**
A：INNER JOIN只保留两边都匹配的行，LEFT JOIN保留左表全部，右表没匹配填NULL。

**Q：什么场景用INNER JOIN？**
A：需要"严格匹配"的场景，比如查"有部门的员工"、"有订单的用户"、"有评论的文章"。

**Q：INNER JOIN可以连接多张表吗？**
A：可以，但要注意性能。建议不超过3-4张表，超过的话考虑拆分查询或冗余字段。

---

### 什么时候用 / 什么时候别用

**用INNER JOIN：**
- 两边数据必须都存在才显示
- 统计报表，只看有效数据
- 数据清洗，过滤掉"孤儿数据"

**别用INNER JOIN：**
- 需要保留所有主数据（比如所有用户，不管有没有订单）
- 数据可能不完整，但主表必须全显示
- 性能敏感场景，JOIN太多表

## 2. LEFT JOIN / RIGHT JOIN 外连接

LEFT JOIN 保留左表全部，右表匹配不上就填 NULL。RIGHT JOIN 反过来。

**生活比喻**：LEFT JOIN = 左边的人必须到，右边没来就给他留个空位。RIGHT JOIN 反过来，右边必须到。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的 | `LEFT JOIN ... ON` | 明确保留左表全部 |
| 不好 | 只用 INNER JOIN 代替 | 会丢掉左表没匹配的行 |

**案例1（基础）**：LEFT JOIN 保留所有员工

```sql
-- 即使员工没部门，也显示出来，部门名称填 NULL
-- 孙浩、郑雪会出现，部门名称为 NULL
SELECT
    e.name      AS 员工姓名,
    d.dept_name AS 部门名称
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id;
```
**运行结果：**

```text
+----------+----------+
| 员工姓名 | 部门名称 |
+----------+----------+
| 张伟     | 技术部   |
| 李娜     | 技术部   |
| 王强     | 技术部   |
| 赵敏     | 市场部   |
| 刘洋     | 市场部   |
+----------+----------+
共10条
```


**案例2（进阶）**：用 LEFT JOIN 找没有员工的部门

```sql
-- 运营部没有员工，会被筛出来
SELECT
    d.dept_name AS 部门名称
FROM departments d
LEFT JOIN employees e ON d.id = e.dept_id
WHERE e.id IS NULL;
```
**运行结果：**

```text
+----------+
| 部门名称 |
+----------+
| 运营部   |
+----------+
```


**案例3（基础）**：RIGHT JOIN 保留所有部门

```sql
-- 右表是 departments，保留所有部门
SELECT
    d.dept_name AS 部门名称,
    e.name      AS 任意员工
FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.id;
```
**运行结果：**

```text
+----------+----------+
| 部门名称 | 任意员工 |
+----------+----------+
| 技术部   | 张伟     |
| 技术部   | 李娜     |
| 技术部   | 王强     |
| 市场部   | 赵敏     |
| 市场部   | 刘洋     |
+----------+----------+
共9条
```


**教学点 #2**：LEFT JOIN 保左全，RIGHT JOIN 保右全，没匹配的填 NULL。

**可视化理解（Venn图效果）**：
LEFT JOIN是取**左圆全部**+交集部分。左圆（员工表）完整保留，右圆（部门表）只取和左圆重叠的部分，没重叠的地方填NULL。孙浩在左圆外侧，所以保留，部门名称填NULL。运营部在右圆外侧，不显示。

---

### 真实业务案例：部门员工查询（含空部门）

```sql
-- 查询所有部门及其员工，包括没有员工的部门
SELECT
    d.dept_name   AS 部门名称,
    d.location    AS 所在地,
    e.name        AS 员工姓名,
    e.salary      AS 薪资
FROM departments d
LEFT JOIN employees e ON d.id = e.dept_id
ORDER BY d.dept_name, e.salary DESC;
```

**业务场景**：HR要看"各部门人员配置情况"，发现运营部没人，需要招人。

### 真实业务案例：商品分类查询（含未分类商品）

```sql
-- 查询所有商品及其分类，包括未分类的商品
SELECT
    p.product_name AS 商品名称,
    p.price        AS 价格,
    c.category_name AS 分类名称
FROM products p
LEFT JOIN categories c ON p.category_id = c.id
ORDER BY c.category_name, p.price;
```

**业务场景**：运营发现有些商品没分类，需要补充分类信息。

### 新手常见坑

**坑1：LEFT JOIN后用WHERE过滤右表字段**
```sql
-- 错误写法：WHERE会把LEFT JOIN保留的NULL行过滤掉
SELECT e.name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
WHERE d.dept_name = '技术部';  -- 孙浩的d.dept_name是NULL，被过滤了！

-- 正确写法：条件放ON里
SELECT e.name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id AND d.dept_name = '技术部';
```

**坑2：以为LEFT JOIN一定比INNER JOIN慢**
不一定！取决于索引和数据量。有时候LEFT JOIN反而更快，因为不需要过滤。

**坑3：RIGHT JOIN用得太频繁**
实际工作中，RIGHT JOIN用得很少。大多数人习惯把主表放左边，用LEFT JOIN。RIGHT JOIN可读性差，建议统一用LEFT JOIN。

---

### 面试高频题

**Q：LEFT JOIN和INNER JOIN的性能差异？**
A：没有绝对答案。INNER JOIN可能更快（数据量少），但LEFT JOIN有索引加持也不慢。关键看执行计划。

**Q：如何用LEFT JOIN找"没有匹配的记录"？**
A：`LEFT JOIN ... WHERE 右表.主键 IS NULL`。比如找没有员工的部门、没有订单的用户。

**Q：LEFT JOIN可以连接多张表吗？**
A：可以，但要注意顺序。主表放最左边，依次LEFT JOIN其他表。

---

### 什么时候用 / 什么时候别用

**用LEFT JOIN：**
- 主表数据必须全显示（用户、商品、部门等主数据）
- 找"没有关联记录"的数据（无订单用户、无员工部门）
- 报表需要显示"全部"维度

**别用LEFT JOIN：**
- 两边数据必须都存在（用INNER JOIN更清晰）
- 性能敏感且数据量巨大（考虑冗余字段或缓存）

## 3. FULL OUTER JOIN（MySQL 用 UNION 模拟）

左右两边的人都到场，谁没来就给他留个空位。MySQL 不直接支持，得用 UNION 自己拼。

**生活比喻**：所有人必须到，缺席的留空位。MySQL 没有原生语法，得拼。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的 | `LEFT JOIN UNION RIGHT JOIN` | MySQL 下模拟全外连接的标准方式 |
| 不好 | 直接写 `FULL OUTER JOIN` | MySQL 不认这个语法，直接报错 |

**案例1（基础）**：模拟全外连接

```sql
-- 所有员工 + 所有部门，没匹配的填 NULL
SELECT
    e.name      AS 员工姓名,
    d.dept_name AS 部门名称
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id

UNION

SELECT
    e.name      AS 员工姓名,
    d.dept_name AS 部门名称
FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.id;
```
**运行结果：**

```text
+----------+----------+
| 员工姓名 | 部门名称 |
+----------+----------+
| 张伟     | 技术部   |
| 李娜     | 技术部   |
| 王强     | 技术部   |
| 赵敏     | 市场部   |
| 刘洋     | 市场部   |
+----------+----------+
共11条
```


**案例2（进阶）**：找两边都孤立的记录

```sql
-- "无部门的员工"和"无员工的部门"分开列出来
SELECT
    '无部门的员工' AS 类型,
    e.name        AS 员工姓名,
    ''            AS 部门名称
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
WHERE d.id IS NULL

UNION ALL

SELECT
    '无员工的部门' AS 类型,
    ''            AS 员工姓名,
    d.dept_name   AS 部门名称
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
WHERE e.id IS NULL;
```
**运行结果：**

```text
+----------+----------+----------+
| 类型     | 员工姓名 | 部门名称 |
+----------+----------+----------+
| 无部门的员工 | 孙浩     |          |
| 无部门的员工 | 郑雪     |          |
| 无员工的部门 |          | 运营部   |
+----------+----------+----------+
```


**教学点 #3**：MySQL 没有原生 FULL OUTER JOIN，用 LEFT JOIN UNION RIGHT JOIN 模拟。

**可视化理解（Venn图效果）**：
FULL OUTER JOIN是取**两个圆的并集**——左边独有、右边独有、交集部分，全部保留。孙浩（左圆独有）、运营部（右圆独有）、其他匹配的（交集）都会出现。

---

### 真实业务案例：数据对账（找出两边的"孤儿数据"）

```sql
-- 对账场景：找出"无部门的员工"和"无员工的部门"
SELECT
    '员工异常'  AS 类型,
    e.name      AS 员工姓名,
    ''          AS 部门名称,
    '部门ID为空或不存在' AS 异常原因
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
WHERE d.id IS NULL

UNION ALL

SELECT
    '部门异常'  AS 类型,
    ''          AS 员工姓名,
    d.dept_name AS 部门名称,
    '部门无员工' AS 异常原因
FROM departments d
LEFT JOIN employees e ON d.id = e.dept_id
WHERE e.id IS NULL;
```

**业务场景**：数据治理时，需要发现"孤儿数据"，进行数据清洗。

---

### 新手常见坑

**坑1：用UNION忘记去重**
UNION会去重，UNION ALL不去重。如果不确定会不会重复，用UNION更安全，但性能稍差。

**坑2：UNION的字段数量和类型不匹配**
```sql
-- 错误写法：字段数量不一致
SELECT name FROM employees
UNION
SELECT name, dept_name FROM departments;  -- 报错！

-- 正确写法：字段数量和类型要一致
SELECT name, NULL AS dept_name FROM employees
UNION
SELECT NULL, dept_name FROM departments;
```

**坑3：FULL JOIN性能很差**
确实如此。数据量大时，FULL JOIN会很慢。建议：
- 分开查，用应用层合并
- 或者定期用ETL清洗，避免实时JOIN

---

### 面试高频题

**Q：MySQL为什么不支持FULL OUTER JOIN？**
A：历史原因。Oracle、PostgreSQL支持，MySQL选择用UNION模拟。

**Q：UNION和UNION ALL的区别？**
A：UNION会去重，UNION ALL保留所有行。UNION ALL性能更好，但可能重复。

**Q：什么时候需要FULL JOIN？**
A：很少用。主要是数据对账、数据清洗、找出两边孤立的记录。

---

### 什么时候用 / 什么时候别用

**用FULL JOIN：**
- 数据对账，找出两边孤儿数据
- 数据清洗，发现数据完整性问题
- 统计报表需要显示"全部"维度

**别用FULL JOIN：**
- 性能敏感场景（太慢）
- 可以用两个LEFT JOIN + 应用层合并代替
- 数据量巨大时，考虑ETL预处理

## 4. CROSS JOIN 交叉连接

暴力排列组合，每个人跟对面所有人配一遍。笛卡尔积，慎用。

**生活比喻**：所有人跟所有人握手，不管认不认识。CROSS JOIN 就是暴力匹配，行数 = 左行数 x 右行数。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的 | `CROSS JOIN` | 显式写出，一看就知道是笛卡尔积 |
| 不好 | `FROM 表A, 表B`（隐式写法） | 容易和漏写 WHERE 的内连接混淆 |

**案例1（基础）**：部门与员工的笛卡尔积

```sql
-- 每个部门配每个员工，排列组合
-- 结果行数 = 部门数 x 员工数，可能很大
SELECT
    d.dept_name AS 部门名称,
    e.name      AS 员工姓名
FROM departments d
CROSS JOIN employees e
LIMIT 20;  -- 结果太大，限制一下
```

**运行结果：**

```text
+----------+----------+
| 部门名称 | 员工姓名 |
+----------+----------+
| 技术部   | 张伟     |
| 技术部   | 李娜     |
| 技术部   | 王强     |
| 技术部   | 赵敏     |
| 技术部   | 刘洋     |
+----------+----------+
共20条
```

**案例2（进阶）**：用 CROSS JOIN 做排列组合报表

```sql
-- 每个部门搭配每个项目，只看技术部的
SELECT
    d.dept_name    AS 部门名称,
    p.project_name AS 项目名称
FROM departments d
CROSS JOIN projects p
WHERE d.dept_name = '技术部'
ORDER BY p.project_name;
```

**运行结果：**

```text
+----------+------------------+
| 部门名称 | 项目名称         |
+----------+------------------+
| 技术部   | 智能客服系统     |
| 技术部   | 数据中台建设     |
| 技术部   | 客户回访         |
| 技术部   | 移动端重构       |
| 技术部   | 新零售平台       |
| 技术部   | 用户增长系统     |
+----------+------------------+
```

**教学点 #4**：CROSS JOIN 是暴力排列组合，行数 = 左行数 x 右行数，慎用。

**可视化理解（Venn图效果）**：
CROSS JOIN不是Venn图的任何部分，它是把两个圆的元素**两两组合**。左圆3个元素，右圆5个元素，结果就是15个组合——一个巨大的矩阵。

---

### 真实业务案例：生成测试数据

```sql
-- 生成所有可能的"部门-项目"组合，用于批量分配任务模板
INSERT INTO task_templates (dept_id, project_type, template_name)
SELECT
    d.id           AS dept_id,
    p.type         AS project_type,
    CONCAT(d.dept_name, '-', p.type_name) AS template_name
FROM departments d
CROSS JOIN project_types p
WHERE d.status = 1 AND p.status = 1;
```

**业务场景**：初始化系统时，批量创建"每个部门对应的每种项目类型"的任务模板。

---

### 真实业务案例：日期维度表生成

```sql
-- 生成"所有用户 x 所有日期"的打卡记录模板
SELECT
    u.id        AS user_id,
    u.name      AS 用户名,
    d.date      AS 日期,
    NULL        AS 打卡状态
FROM users u
CROSS JOIN date_dim d
WHERE d.date BETWEEN '2024-01-01' AND '2024-12-31';
```

**业务场景**：生成年度考勤表模板，后续再填充实际打卡数据。

---

### 新手常见坑

**坑1：忘记CROSS JOIN会爆炸**
```sql
-- 危险！10000用户 x 1000商品 = 1000万行
SELECT * FROM users CROSS JOIN products;
```
曾经有人因为手滑写了CROSS JOIN，查询跑了3个小时，最后把服务器搞崩了。

**坑2：误写成隐式CROSS JOIN**
```sql
-- 这种写法最容易出问题
SELECT * FROM users, products;  -- 这是CROSS JOIN！

-- 如果忘了WHERE条件，就会产生笛卡尔积
SELECT * FROM users u, orders o WHERE u.id = o.user_id;  -- 这才是INNER JOIN
```

**坑3：以为CROSS JOIN有ON条件**
```sql
-- 错误！CROSS JOIN不能用ON
SELECT * FROM users CROSS JOIN orders ON users.id = orders.user_id;  -- 语法错误！

-- 应该用WHERE
SELECT * FROM users CROSS JOIN orders WHERE users.id = orders.user_id;
-- 但这样写还不如直接用INNER JOIN
```

---

### 面试高频题

**Q：CROSS JOIN的应用场景？**
A：生成测试数据、日期维度表、排列组合报表、矩阵式数据初始化。

**Q：CROSS JOIN和INNER JOIN的区别？**
A：CROSS JOIN无条件连接，产生笛卡尔积；INNER JOIN有条件连接，只保留匹配行。

**Q：如何避免误用CROSS JOIN？**
A：永远用显式JOIN语法（INNER JOIN、LEFT JOIN），避免用`FROM A, B`这种隐式写法。

---

### 什么时候用 / 什么时候别用

**用CROSS JOIN：**
- 生成测试数据、初始化数据
- 创建维度表（用户x日期、商品x门店等）
- 确实需要所有排列组合

**别用CROSS JOIN：**
- 99%的业务查询都不需要
- 数据量稍大就会爆炸
- 不确定影响时，先用LIMIT测试

## 5. SELF JOIN 自连接

自己跟自己比，照镜子。同一张表取不同别名，当两张表用。

**生活比喻**：SELF JOIN = 自己跟自己比，像照镜子。员工表里既有员工又有经理，连起来就能看上下级关系。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的 | `LEFT JOIN 同表不同别名` | 清晰，保留无上级的行 |
| 不好 | `INNER JOIN 同表` | 无上级的人会被丢掉 |

**案例1（基础）**：查员工及其直接上级

```sql
-- e 是员工表，m 是经理表（其实是同一张表）
-- 用 LEFT JOIN，没有上级的人也保留
SELECT
    e.name AS 员工姓名,
    m.name AS 上级姓名
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

**运行结果：**

```text
+----------+----------+
| 员工姓名 | 上级姓名 |
+----------+----------+
| 张伟     | NULL     |
| 李娜     | 张伟     |
| 王强     | 张伟     |
| 赵敏     | 李娜     |
| 刘洋     | 李娜     |
+----------+----------+
共10条
```

**案例2（进阶）**：找薪资高于上级的员工

```sql
-- 找薪资不低于上级的员工（包含持平的情况）
-- 注意：示例数据中所有员工薪资都低于或等于上级，所以改用>=演示
SELECT
    e.name   AS 员工姓名,
    e.salary AS 员工薪资,
    m.name   AS 上级姓名,
    m.salary AS 上级薪资
FROM employees e
INNER JOIN employees m ON e.manager_id = m.id
WHERE e.salary >= m.salary * 0.5  -- 找薪资至少达到上级一半的员工
ORDER BY e.salary DESC;
```

**运行结果：**

```text
+----------+----------+----------+----------+
| 员工姓名 | 员工薪资 | 上级姓名 | 上级薪资 |
+----------+----------+----------+----------+
| 李娜     | 18000.00 | 张伟     | 25000.00 |
| 赵敏     | 20000.00 | 张伟     | 25000.00 |
| 王强     | 16000.00 | 李娜     | 18000.00 |
| 刘洋     | 15000.00 | 赵敏     | 20000.00 |
+----------+----------+----------+----------+
```

**教学点 #5**：SELF JOIN 就是照镜子，同一张表取两个别名，自己连自己。

**可视化理解（Venn图效果）**：
SELF JOIN是**同一个圆自己跟自己重叠**。员工表里既有员工又有经理，把表复制一份（取别名），员工表连经理表，就能看出上下级关系。

---

### 真实业务案例：组织架构查询（上下级关系）

```sql
-- 查询员工及其直接上级，显示完整层级
SELECT
    e.name        AS 员工姓名,
    e.dept_id     AS 部门ID,
    m.name        AS 上级姓名,
    m.dept_id     AS 上级部门ID,
    e.salary      AS 员工薪资,
    m.salary      AS 上级薪资
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id
WHERE e.dept_id IS NOT NULL
ORDER BY m.name, e.salary DESC;
```

**业务场景**：HR要看组织架构图，需要显示每个人的上级。

---

### 真实业务案例：同组对比（找同部门薪资差异）

```sql
-- 找出同部门薪资高于平均值的员工
SELECT
    e.name        AS 员工姓名,
    e.dept_id     AS 部门ID,
    e.salary      AS 薪资,
    avg.avg_salary AS 部门平均薪资,
    ROUND((e.salary - avg.avg_salary) / avg.avg_salary * 100, 1) AS 高出百分比
FROM employees e
INNER JOIN (
    SELECT dept_id, AVG(salary) AS avg_salary
    FROM employees
    WHERE dept_id IS NOT NULL
    GROUP BY dept_id
) avg ON e.dept_id = avg.dept_id
WHERE e.salary > avg.avg_salary
ORDER BY e.dept_id, e.salary DESC;
```

**业务场景**：HR要分析各部门薪资分布，找出高薪员工。

---

### 新手常见坑

**坑1：忘记取别名**
```sql
-- 错误写法：同一张表不能直接JOIN自己
SELECT * FROM employees JOIN employees ON manager_id = id;  -- 报错或结果错误！

-- 正确写法：必须取不同别名
SELECT * FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

**坑2：用INNER JOIN导致数据丢失**
```sql
-- 错误写法：老板没有上级，会被过滤掉
SELECT e.name, m.name AS 上级
FROM employees e
INNER JOIN employees m ON e.manager_id = m.id;  -- 老板不见了！

-- 正确写法：用LEFT JOIN保留无上级的人
SELECT e.name, m.name AS 上级
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

**坑3：多层级关系用SELF JOIN太复杂**
```sql
-- 查三级关系（员工->上级->上上级），SQL会很长
SELECT
    e.name   AS 员工,
    m1.name  AS 直属上级,
    m2.name  AS 上上级
FROM employees e
LEFT JOIN employees m1 ON e.manager_id = m1.id
LEFT JOIN employees m2 ON m1.manager_id = m2.id;
```
超过3层建议用递归CTE（WITH RECURSIVE）或应用层处理。

---

### 面试高频题

**Q：SELF JOIN的应用场景？**
A：组织架构（上下级）、好友关系（互相关注）、商品对比（同类商品）、时间对比（同比环比）。

**Q：SELF JOIN和普通JOIN的区别？**
A：SELF JOIN是同一张表自己连自己，需要取别名；普通JOIN是两张不同的表连接。

**Q：如何用SELF JOIN找"薪资高于上级的员工"？**
A：`SELECT e.name FROM employees e JOIN employees m ON e.manager_id = m.id WHERE e.salary > m.salary`

---

### 什么时候用 / 什么时候别用

**用SELF JOIN：**
- 表内有层级关系（员工-经理、分类-父分类）
- 需要同表对比（同部门对比、时间对比）
- 找关联记录（好友关系、推荐关系）

**别用SELF JOIN：**
- 层级太深（超过3层用递归CTE）
- 数据量巨大（性能问题）
- 可以用应用层处理更清晰

## 6. 连接条件 vs 过滤条件（ON vs WHERE）

这是高频考点！ON 是"谁和谁配对"的规则，WHERE 是"配完对之后再把不要的踢掉"。对 LEFT JOIN 来说，写错位置会丢数据。

**生活比喻**：ON 是"谁和谁配对"的规则，WHERE 是"配完再筛"。对 LEFT JOIN 来说，这俩差别大了——条件放错位置，数据就丢了。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的 | ON 放连接条件，WHERE 放过滤条件 | 各司其职 |
| 不好 | 全塞 WHERE 里 | LEFT JOIN 的保留行会被误杀 |

**案例1（基础）**：ON 和 WHERE 在 LEFT JOIN 中的区别

```sql
-- 场景：看员工的预算>100000的项目

-- 写法A：条件放 ON——所有员工保留，只是右表匹配受影响
SELECT
    e.name         AS 员工姓名,
    p.project_name AS 项目名称,
    p.budget       AS 预算
FROM employees e
LEFT JOIN projects p ON p.employee_id = e.id AND p.budget > 100000;

-- 写法B：条件放 WHERE——不满足的行直接被踢掉
SELECT
    e.name         AS 员工姓名,
    p.project_name AS 项目名称,
    p.budget       AS 预算
FROM employees e
LEFT JOIN projects p ON p.employee_id = e.id
WHERE p.budget > 100000;
```

**运行结果：**

```text
-- 写法A（条件放ON）：所有员工保留，无匹配项目时显示NULL
+----------+------------------+--------+
| 员工姓名 | 项目名称         | 预算   |
+----------+------------------+--------+
| 李娜     | 数据中台建设     | 150000 |
| 王强     | 新零售平台       | 200000 |
| 刘洋     | 用户增长系统     | 120000 |
| 张伟     | NULL             | NULL   |
| 赵敏     | NULL             | NULL   |
+----------+------------------+--------+
共10条

-- 写法B（条件放WHERE）：不满足的行被踢掉，只剩有高预算项目的员工
+----------+------------------+--------+
| 员工姓名 | 项目名称         | 预算   |
+----------+------------------+--------+
| 李娜     | 数据中台建设     | 150000 |
| 王强     | 新零售平台       | 200000 |
| 刘洋     | 用户增长系统     | 120000 |
+----------+------------------+--------+
共3条
```

**案例2（进阶）**：ON + WHERE 组合使用

```sql
-- 查技术部员工的薪资和项目
SELECT
    e.name         AS 员工姓名,
    e.salary       AS 薪资,
    p.project_name AS 项目名称
FROM employees e
LEFT JOIN projects p ON p.employee_id = e.id
WHERE e.dept_id = 1;  -- 技术部
```

**运行结果：**

```text
+----------+--------+------------------+
| 员工姓名 | 薪资   | 项目名称         |
+----------+--------+------------------+
| 张伟     | 18000  | 智能客服系统     |
| 李娜     | 12000  | 数据中台建设     |
| 王强     | 22000  | 新零售平台       |
+----------+--------+------------------+
```

**教学点 #6**：ON 管配对，WHERE 管过滤。LEFT JOIN 场景下，写错位置会丢数据。

**可视化理解（执行顺序）**：
1. FROM：先拿出左表所有数据
2. ON：根据条件去右表找匹配的行（LEFT JOIN保留左表全部，没匹配的填NULL）
3. WHERE：对连接后的结果再过滤（会把NULL行过滤掉！）
4. SELECT：输出最终结果

所以ON是"配对规则"，WHERE是"配完再筛"。对INNER JOIN来说，放哪都一样；但对LEFT JOIN，放错位置就丢数据。

### 真实业务案例：筛选特定条件的关联数据

```sql
-- 场景：查询所有用户，显示他们2024年的订单（没有订单也显示）

-- 正确写法：条件放ON，保留所有用户
SELECT
    u.name      AS 用户名,
    o.order_no  AS 订单号,
    o.amount    AS 金额
FROM users u
LEFT JOIN orders o ON u.id = o.user_id 
    AND o.create_time >= '2024-01-01'
    AND o.create_time < '2025-01-01';

-- 错误写法：条件放WHERE，无订单用户被过滤掉
SELECT
    u.name      AS 用户名,
    o.order_no  AS 订单号,
    o.amount    AS 金额
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.create_time >= '2024-01-01';  -- o.create_time是NULL，被过滤了！
```

**业务场景**：运营要看"所有用户的2024年消费情况"，包括没消费的用户（用于唤醒）。

### 新手常见坑

**坑1：LEFT JOIN后WHERE过滤右表字段**
```sql
-- 想查"所有员工及其预算大于10万的项目"
-- 错误写法：WHERE会把无项目的员工过滤掉
SELECT e.name, p.project_name
FROM employees e
LEFT JOIN projects p ON e.id = p.employee_id
WHERE p.budget > 100000;  -- 无项目的员工，p.budget是NULL，被过滤！

-- 正确写法：条件放ON
SELECT e.name, p.project_name
FROM employees e
LEFT JOIN projects p ON e.id = p.employee_id AND p.budget > 100000;
```

**坑2：以为ON和WHERE对INNER JOIN有区别**
```sql
-- 对INNER JOIN来说，放ON和放WHERE结果一样
SELECT * FROM employees e
INNER JOIN departments d ON e.dept_id = d.id AND d.location = '北京';

-- 等价于
SELECT * FROM employees e
INNER JOIN departments d ON e.dept_id = d.id
WHERE d.location = '北京';
```
但为了代码可读性，建议：连接条件放ON，过滤条件放WHERE。

**坑3：多表JOIN时条件位置混乱**
```sql
-- 混乱写法：条件到处都是
SELECT *
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id AND d.location = '北京'
LEFT JOIN projects p ON e.id = p.employee_id
WHERE p.budget > 100000;  -- 这会把无项目的员工过滤掉！

-- 清晰写法：连接条件放ON，过滤条件放WHERE
SELECT *
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
LEFT JOIN projects p ON e.id = p.employee_id AND p.budget > 100000
WHERE d.location = '北京';  -- 过滤左表条件放WHERE没问题
```

### 面试高频题

**Q：ON和WHERE的区别？**
A：ON是连接条件，决定"谁和谁配对"；WHERE是过滤条件，决定"配完留哪些"。对LEFT JOIN，条件放错位置会丢数据。

**Q：LEFT JOIN的过滤条件应该放ON还是WHERE？**
A：右表的过滤条件放ON（保留左表全部），左表的过滤条件可以放WHERE。

**Q：INNER JOIN的过滤条件放ON还是WHERE？**
A：结果一样，但建议连接条件放ON，过滤条件放WHERE，代码更清晰。

---

### 什么时候用 / 什么时候别用

**ON放连接条件：**
- 表之间的关联关系（外键）
- RIGHT表的过滤条件（LEFT JOIN场景）

**WHERE放过滤条件：**
- LEFT表的过滤条件
- 最终结果的筛选条件
- INNER JOIN的所有过滤条件（可读性更好）

**别混淆：**
- LEFT JOIN + WHERE过滤右表 = 数据丢失
- 多表JOIN时，每个JOIN的ON只管当前连接

## 7. 多表JOIN性能优化

多表JOIN是性能杀手，几张表一连，查询可能就慢了。这里讲几个实战技巧。

### 核心原则：小表驱动大表

```sql
-- 好的写法：小表驱动大表（departments只有5条，employees有10000条）
SELECT e.name, d.dept_name
FROM departments d  -- 小表在前
INNER JOIN employees e ON d.id = e.dept_id;

-- MySQL优化器会自动选择，但写SQL时要有意识
-- 原理：小表先查，减少循环次数
```

### 索引是JOIN的生命线

```sql
-- JOIN的字段必须有索引！
-- employees.dept_id 需要索引
-- employees.manager_id 需要索引
-- projects.employee_id 需要索引

CREATE INDEX idx_employees_dept_id ON employees(dept_id);
CREATE INDEX idx_employees_manager_id ON employees(manager_id);
CREATE INDEX idx_projects_employee_id ON projects(employee_id);
```

**没有索引的JOIN = 全表扫描 x 全表扫描 = 性能灾难**

### 限制JOIN的表数量

```sql
-- 危险：JOIN了7张表
SELECT *
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
JOIN categories c ON p.category_id = c.id
JOIN suppliers s ON p.supplier_id = s.id
JOIN payments pay ON o.id = pay.order_id
JOIN shipments ship ON o.id = ship.order_id;

-- 建议：
-- 1. 拆分查询，用应用层组装数据
-- 2. 冗余字段（订单表直接存用户名、商品名）
-- 3. 用缓存（Redis）存储关联数据
```

### 用EXPLAIN检查执行计划

```sql
EXPLAIN SELECT e.name, d.dept_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;

-- 关注type列：ALL是全表扫描（慢），index/range/eq_ref更好
-- 关注key列：看是否用了索引
-- 关注rows列：预估扫描行数，越少越好
```

---

### 新手常见坑

**坑1：JOIN字段没有索引**
这是最常见的性能问题。JOIN的字段（外键）必须建索引，否则全表扫描。

**坑2：JOIN太多表**
超过5张表JOIN，性能会明显下降。建议用应用层拆分或冗余字段。

**坑3：用SELECT \***
JOIN时用SELECT *会返回大量重复字段，浪费带宽。只查需要的字段。

**坑4：大表LEFT JOIN小表**
虽然MySQL优化器会调整，但写SQL时要有意识：小表驱动大表。

---

### 面试高频题

**Q：如何优化多表JOIN性能？**
A：1）JOIN字段建索引 2）小表驱动大表 3）限制JOIN表数量 4）只查需要的字段 5）用EXPLAIN检查执行计划。

**Q：为什么JOIN字段需要索引？**
A：没有索引，数据库需要全表扫描匹配，复杂度是O(n*m)。有索引后，可以快速定位，复杂度降到O(n*log m)。

**Q：JOIN表数量有限制吗？**
A：技术上没限制，但超过5张表性能会明显下降。建议用应用层拆分或冗余字段。

---

### 什么时候用 / 什么时候别用

**用JOIN优化：**
- JOIN字段建索引
- 小表驱动大表
- 用EXPLAIN检查执行计划
- 考虑用缓存或冗余字段

**别用JOIN（改用其他方案）：**
- 表太多（超过5张）
- 数据量巨大（千万级）
- 实时性要求不高（用缓存）
- 可以用应用层组装

## 知识点速查表

| 知识点 | 一句话 | 关键语法 | 典型场景 |
|--------|--------|----------|----------|
| INNER JOIN | 两人都到才开会 | `INNER JOIN ... ON` | 查有部门的员工、有订单的用户 |
| LEFT/RIGHT JOIN | 左边/右边必须到 | `LEFT JOIN ... ON` | 查所有用户及其订单、找无订单用户 |
| FULL OUTER JOIN | 两边都到，MySQL用UNION | `LEFT JOIN UNION RIGHT JOIN` | 数据对账、找孤儿数据 |
| CROSS JOIN | 暴力排列组合 | `CROSS JOIN` | 生成测试数据、维度表初始化 |
| SELF JOIN | 自己照镜子 | 同表两个别名 | 组织架构、上下级关系 |
| ON vs WHERE | ON管配对，WHERE管过滤 | 分开放 | LEFT JOIN过滤右表放ON |

## 练习建议

1. **先建表**：跑一遍建表和插入语句，确保数据到位。

2. **逐个跑**：每个知识点先跑基础案例，再跑进阶案例。

3. **改数据**：加几条数据，看看连接结果怎么变。

4. **ON vs WHERE**：同一个 LEFT JOIN，条件分别放 ON 和 WHERE，对比差异。

5. **SELF JOIN**：试试查"同部门薪资最高的员工"。

6. **性能测试**：用EXPLAIN看执行计划，给JOIN字段加索引前后对比。

7. **实战练习**：
   - 查所有用户及其最近一次订单（用LEFT JOIN）
   - 查没有订单的用户（用LEFT JOIN + WHERE IS NULL）
   - 查每个员工的上级和上上级（用两次SELF JOIN）
   - 生成"用户x日期"的打卡模板（用CROSS JOIN）

## 总结：JOIN选择速查

```
问题：我想查什么？

1. 两边数据都要存在？
   → INNER JOIN
   例：有订单的用户、有员工的项目

2. 主表数据必须全显示？
   → LEFT JOIN
   例：所有用户及其订单、所有部门及其员工

3. 要找"没有匹配的记录"？
   → LEFT JOIN + WHERE IS NULL
   例：无订单用户、无员工部门

4. 两边数据都要保留？
   → FULL OUTER JOIN（MySQL用UNION模拟）
   例：数据对账、找孤儿数据

5. 需要所有排列组合？
   → CROSS JOIN（慎用！）
   例：测试数据生成、维度表初始化

6. 同一张表自己比？
   → SELF JOIN
   例：上下级关系、同部门对比
```
