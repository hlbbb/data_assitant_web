## 1. SELECT / FROM 基础查询

一句话：告诉数据库"你要拿什么"和"从哪拿"。

**生活比喻**：去超市买东西——SELECT 就是你写的购物清单，FROM 就是去哪个货架拿。

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `SELECT name, salary FROM employees` | 明确指定列，清清楚楚 |
| 不好的写法 | `SELECT * FROM employees` | 全选虽然方便，但列多的时候又慢又乱，养成坏习惯 |

**案例1（基础）**：

```sql
-- 查询所有员工的姓名和部门
SELECT name, department
FROM employees;
```

**运行结果：**

```text
+--------+------------+
| name   | department |
+--------+------------+
| 张三   | 技术部      |
| 李四   | 市场部      |
| 王五   | 技术部      |
| 赵六   | 人事部      |
| 孙七   | 市场部      |
+--------+------------+
...（共12条）
```

**案例2（进阶）**：

```sql
-- 给列起别名，让结果更好读
-- AS 可以省略，但写上更清晰
SELECT
    name       AS 姓名,
    department AS 部门,
    salary     AS 月薪
FROM employees;
```

**运行结果：**

```text
+--------+--------+--------+
| 姓名   | 部门   | 月薪   |
+--------+--------+--------+
| 张三   | 技术部 | 15000  |
| 李四   | 市场部 | 12000  |
| 王五   | 技术部 | 18000  |
| 赵六   | 人事部 | 10000  |
| 孙七   | 市场部 | 13000  |
+--------+--------+--------+
...（共12条）
```

**教学点 #1**：SELECT 告诉数据库"拿什么"，FROM 告诉它"从哪拿"。别偷懒用 `SELECT *`。

### 实战场景：电商订单查询

```sql
-- 电商场景：查询最近下单的用户姓名和订单金额
-- 只取需要的列，避免拉取订单详情等大字段
SELECT 
    user_name AS 买家,
    order_amount AS 订单金额,
    create_time AS 下单时间
FROM orders
WHERE status = '已支付'
ORDER BY create_time DESC
LIMIT 100;
```

**什么时候用 SELECT 指定列**：
- 查询结果要展示给用户（只取需要的字段）
- 表里有 TEXT/BLOB 大字段（不指定会全拉出来，慢得要死）
- 写接口返回 JSON（字段越少，传输越快）

**什么时候可以用 SELECT \***：
- 自己临时查数据排查问题（图省事）
- 表结构简单、列数少（比如配置表就 3-5 列）
- 写子查询时外层已经限定了列（但最好还是明确写）

---

### 新手常见坑

1. **SELECT * 配合 JOIN**：两张表都有 `id` 列，结果出来两个 `id`，程序里取值会乱套
2. **忘记起别名**：`SELECT salary * 12` 出来的列名叫 `salary * 12`，程序里很难取
3. **大表全量查询**：百万级表用 `SELECT *`，数据库直接卡死，可能拖垮整个服务

---

### 面试高频题

1. **为什么生产环境不建议用 `SELECT *`？**
   - 答案要点：网络传输开销大、无法利用覆盖索引、表结构变更时可能破坏代码、大字段拖慢查询

2. **SELECT 执行顺序是什么？**
   - 答案要点：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT（SELECT 不是第一个执行的）

## 2. WHERE 条件过滤

一句话：WHERE 是个筛子，帮你把不要的行筛掉，只留满足条件的。

**生活比喻**：淘金——WHERE 就是那个筛子，把沙子漏掉，把金子留下。

**语法**：`SELECT ... FROM 表 WHERE 条件`

支持的运算符：

| 运算符 | 含义 | 例子 |
|--------|------|------|
| `=` | 等于 | `department = '技术部'` |
| `!=` / `<>` | 不等于 | `department != '技术部'` |
| `>` / `<` | 大于 / 小于 | `salary > 10000` |
| `BETWEEN ... AND ...` | 在范围内（含边界） | `salary BETWEEN 10000 AND 15000` |
| `IN (...)` | 在集合中 | `department IN ('技术部','市场部')` |
| `LIKE` | 模糊匹配 | `name LIKE '张%'` |

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `WHERE salary BETWEEN 10000 AND 15000` | 范围查询，语义清晰 |
| 不好的写法 | `WHERE salary >= 10000 AND salary <= 15000` | 功能一样，但啰嗦 |

**案例1（基础）**：

```sql
-- 查询技术部且薪资大于16000的员工
SELECT name, salary
FROM employees
WHERE department = '技术部' AND salary > 16000;
```

**运行结果：**

```text
+------+--------+
| name | salary |
+------+--------+
| 王五 | 18000  |
| 周八 | 20000  |
+------+--------+
```

**案例2（进阶）**：

```sql
-- 查询薪资在10000到15000之间的市场部或人事部员工
-- BETWEEN 含边界，IN 匹配集合
SELECT name, department, salary
FROM employees
WHERE salary BETWEEN 10000 AND 15000
  AND department IN ('市场部', '人事部');
```

**运行结果：**

```text
+------+------------+--------+
| name | department | salary |
+------+------------+--------+
| 李四 | 市场部     | 12000  |
| 赵六 | 人事部     | 10000  |
| 孙七 | 市场部     | 13000  |
| 郑十 | 市场部     | 11000  |
+------+------------+--------+
```

**教学点 #2**：WHERE 是筛子。`=` 精确匹配，`BETWEEN` 范围匹配，`IN` 集合匹配，`LIKE` 模糊匹配，各有所长。

### 实战场景：财务系统对账

```sql
-- 财务场景：查询某时间段内、特定状态的订单，用于对账
SELECT 
    order_no AS 订单号,
    amount AS 金额,
    status AS 状态,
    pay_time AS 支付时间
FROM orders
WHERE pay_time BETWEEN '2024-01-01' AND '2024-01-31'
  AND status IN ('已支付', '已退款')
  AND amount > 0
ORDER BY pay_time;
```

**什么时候用 BETWEEN**：
- 时间范围查询（注意：BETWEEN 含边界，`BETWEEN '2024-01-01' AND '2024-01-31'` 包含 31 号 00:00:00，但不包含 31 号 23:59:59）
- 数值范围查询（价格区间、年龄区间）

**什么时候用 IN**：
- 枚举值匹配（状态字段：待支付/已支付/已取消）
- 多个 ID 查询（`WHERE user_id IN (1, 2, 3, 5, 8)`）
- 子查询结果匹配（`WHERE department_id IN (SELECT id FROM departments WHERE ...)`）

**什么时候用 LIKE**：
- 搜索功能（商品名、用户名模糊搜索）
- 前缀匹配可以用索引（`LIKE '张%'` 能走索引，`LIKE '%张'` 走不了）

---

### 新手常见坑

1. **BETWEEN 时间范围边界问题**：查 1 月数据用 `BETWEEN '2024-01-01' AND '2024-01-31'`，结果漏了 31 号下午的数据。正确写法：`>= '2024-01-01' AND < '2024-02-01'`
2. **IN 列表太长**：`IN (1,2,3,...,10000)` 列表写了几万个值，SQL 语句超长，数据库解析慢。建议用临时表或子查询
3. **LIKE 左模糊**：`LIKE '%张'` 全表扫描，百万级数据直接卡死。能避免就避免，或者用全文索引

---

### 面试高频题

1. **BETWEEN 和 >= ... AND <= 有什么区别？**
   - 答案要点：语义上 BETWEEN 更清晰，但要注意时间类型的边界问题；BETWEEN 在某些数据库中优化器处理更好

2. **LIKE 什么情况下能走索引？**
   - 答案要点：前缀匹配 `LIKE 'abc%'` 能走索引，后缀匹配 `LIKE '%abc'` 和全模糊 `LIKE '%abc%'` 走不了（除非用全文索引或倒排索引）

## 3. AND / OR / NOT 逻辑运算

一句话：AND 是"并且"，OR 是"或者"，NOT 是"反过来"。

**生活比喻**：点外卖——AND 是"要麻辣且加蛋"，OR 是"麻辣或酸甜都行"，NOT 是"不要香菜"。

**语法**：`WHERE 条件1 AND/OR 条件2`，`WHERE NOT 条件`

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `WHERE (a AND b) OR (c AND d)` | 括号一加，逻辑清清楚楚 |
| 不好的写法 | `WHERE a AND b OR c AND d` | 优先级搞混，结果可能不是你要的 |

**案例1（基础）**：

```sql
-- 查询技术部且年龄>=30，或者市场部且年龄>=28的员工
-- 注意括号！AND优先级高于OR，不加括号逻辑会乱
SELECT name, department, age
FROM employees
WHERE (department = '技术部' AND age >= 30)
   OR (department = '市场部' AND age >= 28);
```

**运行结果：**

```text
+--------+------------+-----+
| name   | department | age |
+--------+------------+-----+
| 王五   | 技术部     |  35 |
| 周八   | 技术部     |  40 |
| 钱十一 | 技术部     |  33 |
| 李四   | 市场部     |  32 |
| 孙七   | 市场部     |  30 |
| 郑十   | 市场部     |  29 |
+--------+------------+-----+
```

**案例2（进阶）**：

```sql
-- 查询不在技术部和市场部的员工（部门不为空）
-- NOT IN 取反
SELECT name, department
FROM employees
WHERE department IS NOT NULL
  AND department NOT IN ('技术部', '市场部');
```

**运行结果：**

```text
+--------+------------+
| name   | department |
+--------+------------+
| 赵六   | 人事部      |
| 吴九   | 人事部      |
| 陈十二 | 财务部      |
| 林十三 | 财务部      |
+--------+------------+
```

**教学点 #3**：AND 优先级高于 OR。拿不准就加括号，括号不花钱。

### 实战场景：HR 系统薪资筛选

```sql
-- HR场景：筛选候选人
-- 要么是技术岗且5年以上经验，要么是管理岗且3年以上经验
SELECT 
    name AS 姓名,
    position AS 岗位,
    experience AS 经验年限,
    expected_salary AS 期望薪资
FROM candidates
WHERE (position = '技术岗' AND experience >= 5)
   OR (position = '管理岗' AND experience >= 3)
ORDER BY expected_salary DESC;
```

```sql
-- 另一个场景：排除某些条件
-- 查询入职超过1年、但还没离职、也不在试用期的人
SELECT name, department, hire_date
FROM employees
WHERE hire_date <= DATE_SUB(NOW(), INTERVAL 1 YEAR)
  AND status != '离职'
  AND NOT (probation = 1);  -- 也可以写成 AND probation = 0
```

**什么时候用 AND**：
- 多个条件必须同时满足（技术部 AND 薪资>15000 AND 在职）
- 缩小结果集（条件越多，结果越少）

**什么时候用 OR**：
- 多个条件满足其一即可（技术部 OR 市场部）
- 扩大结果集（条件越多，结果越多）

**什么时候用 NOT**：
- 排除特定值（NOT IN、NOT BETWEEN、NOT LIKE）
- 反向逻辑更清晰时（`NOT (status = '离职')` 比 `status != '离职'` 更强调"排除离职"）

---

### 新手常见坑

1. **AND/OR 混用不加括号**：`WHERE dept = '技术部' AND salary > 10000 OR age > 30`，你以为查的是"技术部且高薪"或"年龄大的人"，实际数据库理解成 `(技术部 AND 高薪) OR (年龄大)`，连市场部年龄大的都出来了
2. **NOT IN 遇到 NULL**：`WHERE id NOT IN (1, 2, NULL)` 结果是空的！因为 `id != NULL` 永远是 NULL（未知），整个条件就失效了
3. **条件太复杂看不懂**：一堆 AND/OR 嵌套，三个月后自己都看不懂。建议拆成多条 SQL，或者用 CASE WHEN 先标记

---

### 面试高频题

1. **AND 和 OR 的优先级谁高？**
   - 答案要点：AND 优先级高于 OR，所以 `a OR b AND c` 等价于 `a OR (b AND c)`。不确定就加括号

2. **NOT IN 子查询遇到 NULL 会怎样？**
   - 答案要点：`WHERE id NOT IN (SELECT ...)` 如果子查询返回 NULL，整个 WHERE 条件会变成"未知"，结果为空。建议用 NOT EXISTS 替代

---

## 4. ORDER BY 排序（ASC / DESC）

一句话：给结果排个序，升序还是降序你说了算。

**生活比喻**：排队——ASC 是从矮到高排，DESC 是从高到矮排。默认是 ASC。

**语法**：`ORDER BY 列名 ASC/DESC`，多列排序用逗号隔开

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `ORDER BY salary DESC` | 语义清晰，明确指定方向 |
| 不好的写法 | `ORDER BY salary` | 省略 ASC 也能跑，但不够明确，容易忘 |

**案例1（基础）**：

```sql
-- 按薪资降序排列，看看谁是薪资天花板
SELECT name, salary
FROM employees
ORDER BY salary DESC;
```

**运行结果：**

```text
+--------+--------+
| name   | salary |
+--------+--------+
| 周八   | 20000  |
| 王五   | 18000  |
| 钱十一 | 16000  |
| 张三   | 15000  |
| 陈十二 | 14000  |
+--------+--------+
...（共12条）
```

**案例2（进阶）**：

```sql
-- 先按部门升序，再按薪资降序
-- 同一部门内，薪资高的排前面
SELECT name, department, salary
FROM employees
ORDER BY department ASC, salary DESC;
```

**运行结果：**

```text
+--------+------------+--------+
| name   | department | salary |
+--------+------------+--------+
| 黄十四 | NULL       | 8500   |
| 赵六   | 人事部     | 10000  |
| 吴九   | 人事部     | 9500   |
| 孙七   | 市场部     | 13000  |
| 李四   | 市场部     | 12000  |
+--------+------------+--------+
...（共12条）
```

**教学点 #4**：ORDER BY 排序，ASC 升序 DESC 降序。多列排序时，写在前面的先排。

---

### 实战场景：电商商品列表排序

```sql
-- 电商场景：商品列表排序
-- 先按销量降序（卖得好的排前面），同销量再按价格升序（便宜的排前面）
SELECT 
    product_name AS 商品名称,
    price AS 价格,
    sales AS 销量,
    stock AS 库存
FROM products
WHERE stock > 0
ORDER BY sales DESC, price ASC
LIMIT 50;
```

```sql
-- 另一个场景：财务对账单按日期排序
-- 同一天按金额降序，方便对账
SELECT 
    trans_date AS 交易日期,
    amount AS 金额,
    type AS 类型,
    remark AS 备注
FROM transactions
WHERE account_id = 10086
ORDER BY trans_date ASC, amount DESC;
```

**什么时候用 ORDER BY**：
- 分页查询（不排序分页没意义，每次查出来的顺序可能不一样）
- 排行榜、Top N（配合 LIMIT 取前几名）
- 报表展示（用户习惯按时间、金额排序）

**什么时候不用 ORDER BY**：
- 数据量超大且不需要固定顺序（排序是耗资源的操作）
- 已知数据本身就是有序的（比如按主键查）

---

### 新手常见坑

1. **分页不加 ORDER BY**：`SELECT * FROM orders LIMIT 0, 10` 和 `LIMIT 10, 10` 可能查出重复数据，因为数据库返回顺序不确定
2. **排序列有 NULL**：`ORDER BY bonus DESC`，NULL 值排在最前还是最后取决于数据库，MySQL 默认 NULL 排最前（降序时）
3. **排序字段没索引**：百万级数据按非索引字段排序，数据库要全表扫描+临时表，慢到飞起

---

### 面试高频题

1. **ORDER BY 多列排序的规则是什么？**
   - 答案要点：按书写顺序依次排序，第一列相同再按第二列，以此类推。每列可以单独指定 ASC/DESC

2. **ORDER BY 为什么慢？如何优化？**
   - 答案要点：没索引时要全表扫描+排序（Filesort）。优化方法：给排序字段加索引、减少返回列（用覆盖索引）、限制结果集大小

---

## 5. LIMIT 限制结果数量

一句话：只要前 N 条，多的不要。

**生活比喻**：自助餐限流——一次只让进 5 个人。LIMIT 就是那个门禁。

**语法**：`LIMIT 数量` 或 `LIMIT 偏移量, 数量`

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `ORDER BY ... LIMIT 10` | 配合 ORDER BY 取 Top N，结果确定 |
| 不好的写法 | `LIMIT 10`（无 ORDER BY） | 没有 ORDER BY 时，取出顺序不确定，结果随机 |

**案例1（基础）**：

```sql
-- 查询薪资最高的3名员工
SELECT name, salary
FROM employees
ORDER BY salary DESC
LIMIT 3;
```

**运行结果：**

```text
+--------+--------+
| name   | salary |
+--------+--------+
| 周八   | 20000  |
| 王五   | 18000  |
| 钱十一 | 16000  |
+--------+--------+
```

**案例2（进阶）**：

```sql
-- 分页查询：第2页，每页5条
-- 偏移量 = (页码-1) * 每页条数 = (2-1)*5 = 5
SELECT name, department, salary
FROM employees
ORDER BY salary DESC
LIMIT 5, 5;  -- 从第5条开始，取5条
```

**运行结果：**

```text
+--------+------------+--------+
| name   | department | salary |
+--------+------------+--------+
| 林十三 | 财务部     | 13500  |
| 孙七   | 市场部     | 13000  |
| 李四   | 市场部     | 12000  |
| 郑十   | 市场部     | 11000  |
| 赵六   | 人事部     | 10000  |
+--------+------------+--------+
```

**教学点 #5**：LIMIT 限制条数，分页用 `LIMIT 偏移量, 条数`。必须配合 ORDER BY，否则结果不稳定。

---

### 实战场景：分页查询

```sql
-- 电商场景：商品列表分页，每页20条
-- 第1页：LIMIT 0, 20
-- 第2页：LIMIT 20, 20
-- 第3页：LIMIT 40, 20
-- 公式：偏移量 = (页码-1) * 每页条数
SELECT
    id AS product_id,
    product_name,
    price
FROM products
WHERE status = '上架'
ORDER BY sort_weight DESC, create_time DESC
LIMIT 0, 20;  -- 第1页
```

```sql
-- 订单管理场景：查询最近100条订单记录
SELECT
    order_no AS 订单号,
    user_name AS 下单用户,
    amount AS 金额,
    create_time AS 下单时间
FROM orders
ORDER BY create_time DESC
LIMIT 100;
```

**什么时候用 LIMIT**：
- 分页展示（列表页、商品页、订单页）
- Top N 排行（销量 Top10、活跃用户 Top100）
- 防止全表扫描（加个 LIMIT 保底，避免误操作拉出百万数据）

**什么时候不用 LIMIT**：
- 需要统计总数（LIMIT 只限制返回条数，不改变 COUNT 的结果）
- 导出全部数据（要导出就别 LIMIT，或者分批导）

---

### 新手常见坑

1. **LIMIT 偏移量太大**：`LIMIT 100000, 20` 查第 5000 页，数据库要先扫描前 100000 条再取 20 条，慢到怀疑人生。优化方案：用 WHERE + 主键定位（`WHERE id > 上一页最后一条id LIMIT 20`）
2. **分页总数计算错误**：前端显示"共 100 页"，实际数据在变，用户点第 100 页可能没数据了。实时性要求高的场景，总数可以缓存或估算
3. **忘记 ORDER BY**：`LIMIT 10` 不加排序，每次查出来的可能不一样，用户刷新页面数据顺序变了，体验很差

---

### 面试高频题

1. **LIMIT 深分页怎么优化？**
   - 答案要点：`LIMIT 100000, 20` 性能差，改用 `WHERE id > 上一页最大id ORDER BY id LIMIT 20`，利用主键索引快速定位

2. **MySQL 和 PostgreSQL 的 LIMIT 语法有什么区别？**
   - 答案要点：MySQL 用 `LIMIT offset, count` 或 `LIMIT count OFFSET offset`；PostgreSQL 用 `LIMIT count OFFSET offset`；SQL Server 用 `OFFSET offset ROWS FETCH NEXT count ROWS ONLY`

---

## 6. DISTINCT 去重

一句话：重复的不要，只留唯一的。

**生活比喻**：一副扑克牌里挑花色——只看有几种花色，不看有几张牌。

**语法**：`SELECT DISTINCT 列名1, 列名2 ...`

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `SELECT DISTINCT department` | 明确去重 |
| 不好的写法 | `GROUP BY department`（仅用于去重） | 功能等效但语义不清，GROUP BY 是分组用的 |

**案例1（基础）**：

```sql
-- 查询所有不重复的部门
SELECT DISTINCT department
FROM employees;
```

**运行结果：**

```text
+------------+
| department |
+------------+
| 技术部      |
| 市场部      |
| 人事部      |
| 财务部      |
| NULL        |
+------------+
```

**案例2（进阶）**：

```sql
-- 多列去重：不重复的 部门+年龄 组合
SELECT DISTINCT department, age
FROM employees
WHERE department IS NOT NULL
ORDER BY department;
```

**运行结果：**

```text
+------------+-----+
| department | age |
+------------+-----+
| 人事部     |  24 |
| 人事部     |  26 |
| 市场部     |  29 |
| 市场部     |  30 |
| 市场部     |  32 |
+------------+-----+
...（共11条）
```

**教学点 #6**：DISTINCT 去重，放列名前面。单列多列都能去，但别拿 GROUP BY 替代它。

---

### 实战场景：下拉选项去重

```sql
-- 电商场景：查询所有上架商品的品牌（用于筛选下拉框）
SELECT DISTINCT brand AS 品牌
FROM products
WHERE status = '上架'
ORDER BY brand;
```

```sql
-- HR场景：查询所有在职员工的部门+年龄段组合（用于人事统计）
SELECT DISTINCT
    department AS 部门,
    CASE
        WHEN age < 25 THEN '年轻'
        WHEN age < 30 THEN '青年'
        WHEN age < 35 THEN '中年'
        ELSE '资深'
    END AS 年龄段
FROM employees
WHERE status = '在职'
  AND department IS NOT NULL
ORDER BY department, 年龄段;
```

**什么时候用 DISTINCT**：
- 下拉选项去重（品牌列表、城市列表、分类列表）
- 查询有哪些值（"这张表里有哪几个部门"）
- 多列组合去重（部门+岗位的唯一组合）

**什么时候别用 DISTINCT**：
- 想统计每个值有多少条（用 GROUP BY + COUNT）
- 数据量超大（DISTINCT 要全表扫描+临时表，慢）
- 只是想去除子查询重复（用 EXISTS 替代 IN，或改写查询逻辑）

---

### 新手常见坑

1. **DISTINCT 多列理解错误**：`SELECT DISTINCT department, position` 不是分别去重，而是去重"组合"。结果里可能有多个"技术部"，但每个"技术部+岗位"组合是唯一的
2. **DISTINCT 配合 COUNT**：`COUNT(DISTINCT department)` 统计部门数量，但 `DISTINCT COUNT(department)` 语法错误。注意写法顺序
3. **DISTINCT 和 ORDER BY 冲突**：`SELECT DISTINCT name FROM users ORDER BY id` 报错，因为 ORDER BY 的列不在 SELECT 里（某些数据库允许，但不推荐）

---

### 面试高频题

1. **DISTINCT 和 GROUP BY 有什么区别？**
   - 答案要点：单就去重效果一样，但语义不同——DISTINCT 是"去重"，GROUP BY 是"分组"。GROUP BY 可以配合聚合函数（COUNT/SUM），DISTINCT 不行。语义上该用哪个就用哪个

2. **COUNT(DISTINCT column) 怎么优化？**
   - 答案要点：COUNT(DISTINCT) 要全表扫描，数据量大时很慢。优化：给该列加索引、用近似算法（HyperLogLog）、或者预计算存到汇总表

---

## 7. NULL 值处理（IS NULL / IS NOT NULL）

一句话：NULL 就是"不知道"，不是 0，不是空字符串，是"啥也不是"。

**生活比喻**：问卷上"奖金"那栏空着——不是填了 0，而是压根没填。你得用 IS NULL 去找那些"没填的人"。

**语法**：`WHERE 列 IS NULL` / `WHERE 列 IS NOT NULL`

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `WHERE bonus IS NULL` | 正确判断 NULL |
| 不好的写法 | `WHERE bonus = NULL` | 语法不报错，但永远查不到！NULL 不等于 NULL |

**案例1（基础）**：

```sql
-- 查询没有奖金的员工（bonus 为 NULL）
SELECT name, department
FROM employees
WHERE bonus IS NULL;

-- 查询有奖金的员工
SELECT name, bonus
FROM employees
WHERE bonus IS NOT NULL;
```

**运行结果：**

```text
-- 第一个查询（bonus IS NULL）：
+--------+------------+
| name   | department |
+--------+------------+
| 赵六   | 人事部      |
| 吴九   | 人事部      |
| 林十三 | 财务部      |
| 黄十四 | NULL        |
+--------+------------+

-- 第二个查询（bonus IS NOT NULL）：
+--------+--------+
| name   | bonus  |
+--------+--------+
| 张三   | 3000   |
| 李四   | 2000   |
| 王五   | 5000   |
| 孙七   | 1500   |
| 周八   | 8000   |
+--------+--------+
...（共8条）
```

**案例2（进阶）**：

```sql
-- 用 IFNULL 把 NULL 替换为 0，计算年薪
-- IFNULL(列名, 默认值)：如果是NULL就换成默认值
SELECT
    name                  AS 姓名,
    salary                AS 月薪,
    IFNULL(bonus, 0)      AS 奖金,
    salary * 12 + IFNULL(bonus, 0) AS 年薪
FROM employees;
```

**运行结果：**

```text
+--------+--------+--------+--------+
| 姓名   | 月薪   | 奖金   | 年薪   |
+--------+--------+--------+--------+
| 张三   | 15000  | 3000   | 183000 |
| 李四   | 12000  | 2000   | 146000 |
| 王五   | 18000  | 5000   | 221000 |
| 赵六   | 10000  | 0      | 120000 |
| 孙七   | 13000  | 1500   | 157500 |
+--------+--------+--------+--------+
...（共12条）
```

**教学点 #7**：NULL 不是 0，不是空串。判断用 IS NULL，替换用 IFNULL。千万别写 `= NULL`。

---

### 实战场景：处理缺失数据

```sql
-- 电商场景：查询没有设置收货地址的订单（需要提醒用户补充）
SELECT 
    order_no AS 订单号,
    user_name AS 用户,
    create_time AS 下单时间
FROM orders
WHERE address_id IS NULL
  AND status = '待发货'
ORDER BY create_time;
```

```sql
-- 财务场景：计算员工总薪资，奖金为空时按0处理
-- IFNULL 在 MySQL 中使用，Oracle 用 NVL，SQL Server 用 ISNULL
SELECT
    name AS 姓名,
    salary AS 基本工资,
    IFNULL(bonus, 0) AS 奖金,
    salary + IFNULL(bonus, 0) AS 总薪资
FROM employees
WHERE department = '技术部';
```

```sql
-- HR场景：查询部门为空的员工（可能是数据问题，需要核实）
SELECT 
    name AS 姓名,
    hire_date AS 入职日期,
    '部门未分配' AS 备注
FROM employees
WHERE department IS NULL;
```

**什么时候用 IS NULL**：
- 查询缺失数据（没有填写的信息、未关联的数据）
- 数据质量检查（找出哪些字段有空值）
- 条件分支（有值走一个逻辑，没值走另一个）

**什么时候用 IFNULL/COALESCE**：
- 计算时避免 NULL 污染（任何数 + NULL = NULL，必须先替换）
- 展示时给默认值（奖金为空显示"暂无"或 0）
- 排序时控制 NULL 位置（MySQL 的 `ORDER BY IFNULL(bonus, 0) DESC`）

---

### 新手常见坑

1. **用 = NULL 判断**：`WHERE bonus = NULL` 语法不报错，但永远查不到数据！因为 NULL = NULL 的结果不是 true，而是 NULL（未知）。必须用 `IS NULL`
2. **NULL 参与计算**：`SELECT salary + bonus` 如果 bonus 是 NULL，结果就是 NULL。必须用 `salary + IFNULL(bonus, 0)`
3. **NOT IN 遇到 NULL**：`WHERE id NOT IN (1, 2, NULL)` 结果为空，因为 `id != NULL` 永远是未知。用 NOT EXISTS 或先过滤 NULL
4. **COUNT 和 SUM 对 NULL 的处理不同**：`COUNT(bonus)` 不统计 NULL，`SUM(bonus)` 忽略 NULL。但 `COUNT(*)` 统计所有行，包括 NULL

---

### 面试高频题

1. **NULL 和空字符串有什么区别？**
   - 答案要点：NULL 是"未知/不存在"，空字符串是"确定的空值"。`IS NULL` 能查出 NULL，查不出空字符串。业务上：未填写用 NULL，填写了但为空用空字符串

2. **为什么任何数和 NULL 运算结果都是 NULL？**
   - 答案要点：SQL 标准规定 NULL 表示"未知"，未知数参与运算结果还是未知。这是三值逻辑（true/false/null）的设计

3. **COALESCE 和 IFNULL 有什么区别？**
   - 答案要点：IFNULL 只能处理两个参数，COALESCE 可以处理多个（返回第一个非 NULL 值）。COALESCE 是 SQL 标准，IFNULL 是 MySQL 特有

## 附录：新手常见问题汇总

### Q1：SQL 关键字必须大写吗？
不用。`SELECT` 和 `select` 都能跑，大写只是习惯问题，方便区分关键字和字段名。团队统一风格就行。

### Q2：表名、字段名用中文还是英文？
都可以，MySQL 支持中文表名和字段名。但推荐用英文，一是兼容性好，二是代码里混着中文容易出编码问题。

### Q3：单引号和双引号有什么区别？
SQL 标准里字符串用单引号 `'张三'`，双引号用于标识符（表名、列名）。MySQL 默认都支持，但建议按标准来，单引号包字符串。

### Q4：分号必须写吗？
在客户端里执行单条 SQL 可以不写，但在存储过程、脚本文件里必须写。养成好习惯，每条 SQL 后面都加分号。

### Q5：怎么快速测试 SQL 语句？
推荐用本地数据库（MySQL/PostgreSQL）或在线工具（SQL Fiddle、DB Fiddle），别在生产库上测试。搞个测试表，随便玩。
