# 第六阶段：数据操作与建表

> 从"查数据"进化到"造数据"——学会建表、插数据、改数据、删数据，以及约束、索引、视图、事务这些"规矩"和"工具"。

## 1. INSERT 插入数据——往表格里填一行新数据

一句话：INSERT 就是往表里"塞"一行新数据，可以塞一行，也可以批量塞，还可以把查询结果直接塞进去。

**生活比喻**：就像往 Excel 表格里新增一行记录，手动填也行，复制粘贴也行。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：省略列名，顺序一旦改就炸
INSERT INTO students VALUES (1, '张三', '男', '2005-03-15', '高三1班', '13800001111');

-- ✅ 好的写法：显式指定列名，安全可读
INSERT INTO students (name, gender, birth_date, class_name, phone)
VALUES ('张三', '男', '2005-03-15', '高三1班', '13800001111');
```

**运行结果：**

```text
执行成功，影响1行
```

### 案例1（基础）：单行插入与批量插入

```sql
-- 单行插入
INSERT INTO students (name, gender, birth_date, class_name, phone)
VALUES ('李四', '女', '2005-06-20', '高三2班', '13800002222');

-- 批量插入：一次性插多行，比一条条插快得多
INSERT INTO students (name, gender, birth_date, class_name, phone)
VALUES
    ('王五', '男', '2005-01-10', '高三1班', '13800003333'),
    ('赵六', '女', '2005-09-08', '高三2班', '13800004444'),
    ('钱七', '男', '2005-12-25', '高三1班', '13800005555');

-- 课程表也来一批
INSERT INTO courses (course_name, credit, teacher)
VALUES
    ('数学', 4.0, '王老师'),
    ('英语', 3.0, '李老师'),
    ('物理', 3.5, '张老师');
```

**运行结果：**

```text
执行成功，影响6行（单行插入影响1行 + 批量插入影响3行 + 课程插入影响3行）
```

### 案例2（进阶）：从查询结果插入 + 插入时忽略重复

```sql
-- 把成绩低于60分的记录备份到 scores_backup 表
-- 先建备份表（结构同 scores）
CREATE TABLE scores_backup AS SELECT * FROM scores WHERE 1=0;

-- 从查询结果插入
INSERT INTO scores_backup (student_id, course_id, score, exam_date)
SELECT student_id, course_id, score, exam_date
FROM scores
WHERE score < 60;

-- INSERT IGNORE：遇到唯一键冲突就跳过，不报错
INSERT IGNORE INTO students (name, gender, class_name, phone)
VALUES ('张三', '男', '高三1班', '13800001111');
-- 如果 phone 已存在，这条会被静默跳过

-- ON DUPLICATE KEY UPDATE：冲突时更新
INSERT INTO students (name, gender, class_name, phone)
VALUES ('张三', '男', '高三1班', '13800001111')
ON DUPLICATE KEY UPDATE class_name = VALUES(class_name);
-- phone 冲突时，只更新班级
```

**运行结果：**

```text
scores_backup 表创建成功
备份插入执行成功，影响0行（无低于60分的成绩）
INSERT IGNORE 执行成功，影响1行（跳过重复记录）
ON DUPLICATE KEY UPDATE 执行成功，影响2行（冲突时更新班级）
```

**实战技巧**：
- INSERT IGNORE：适合"有就跳过，没有就插"的场景，比如数据导入时跳过已存在的记录
- ON DUPLICATE KEY UPDATE：适合"有就更新，没有就插入"的场景，比如用户信息同步
- INSERT ... SELECT：适合数据迁移、数据备份、数据清洗

**新手常见坑**：
- 列名顺序搞错：省略列名时，VALUES 的顺序必须和表结构完全一致，少一个字段就炸
- 主键冲突：自增主键不用手动插，硬插会冲突
- 批量插到一半失败：部分数据库会回滚已插入的，MySQL 默认继续，需要用事务保证原子性
- 忘了 NOT NULL 约束：插了 NULL 值才发现约束拦不住，建表时要提前规划

**面试高频题**：
- INSERT、INSERT IGNORE、REPLACE、ON DUPLICATE KEY UPDATE 有啥区别？
- 批量插入 10 万条数据怎么优化？（答案：分批、事务、LOAD DATA INFILE）
- 为什么不推荐用 `INSERT INTO t VALUES (...)`？

**什么时候用/什么时候别用**：
- 用：需要新增数据、数据导入、数据迁移
- 别用：大表批量插入别一条条循环插，用批量 INSERT 或 LOAD DATA
- 小技巧：生产环境批量插入前先备份，或者用事务包裹

## 2. UPDATE 更新数据——涂改液，改掉旧值

一句话：UPDATE 就是把已有数据改一改，可以改一个字段，也可以改多个字段，还能拿子查询的结果来改。

**生活比喻**：就像用涂改液把表格里的旧值涂掉，写上新值。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：忘了 WHERE，全表都改了！
UPDATE students SET class_name = '高三1班';

-- ✅ 好的写法：WHERE 条件精确限定
UPDATE students SET class_name = '高三1班' WHERE student_id = 1;
```

**运行结果：**

```text
执行成功，影响1行
```

### 案例1（基础）：单列与多列更新

```sql
-- 单列更新
UPDATE students SET phone = '13900001111' WHERE student_id = 1;

-- 多列更新：一次改多个字段
UPDATE students
SET class_name = '高三3班', phone = '13900006666'
WHERE student_id = 5;
```

**运行结果：**

```text
执行成功，影响1行
```

### 案例2（进阶）：基于子查询更新 + CASE条件更新

```sql
-- 子查询更新：根据成绩表的数据来更新
-- 给数学成绩大于90的学生班级标记更新
UPDATE scores
SET score = score + 5
WHERE course_id = (SELECT course_id FROM courses WHERE course_name = '数学')
  AND score >= 90;

-- CASE 条件更新：不同条件不同改法
UPDATE students
SET class_name = CASE
    WHEN class_name = '高三1班' THEN '高三A班'
    WHEN class_name = '高三2班' THEN '高三B班'
    ELSE class_name
END;
-- 注意 ELSE 分支保留原值，避免没匹配的被改成 NULL
```

**运行结果：**

```text
子查询更新执行成功，影响0行（数学成绩>=90的记录加5分）
CASE条件更新执行成功，影响5行（高三1班→高三A班，高三2班→高三B班）
```

**新手常见坑**：
- **最致命的坑**：UPDATE 不写 WHERE，全表都被改了！生产环境直接跑路
- 先 SELECT 再 UPDATE：不确定影响范围时，先 `SELECT * FROM t WHERE ...` 看看会改哪些行
- 忘了备份：改错了没备份，只能哭着找 DBA 恢复
- 子查询性能炸裂：UPDATE 里套子查询，大表直接卡死
- CASE 更新忘了 ELSE：没匹配的行会被改成 NULL

**面试高频题**：
- UPDATE 不写 WHERE 会怎样？（全表更新，灾难级）
- 如何安全地执行 UPDATE？（先 SELECT 确认、开事务、备份）
- UPDATE 和 DELETE 哪个更危险？（都危险，但 UPDATE 改错了还能改回来，DELETE 删了就没了）

**什么时候用/什么时候别用**：
- 用：数据修正、状态更新、批量调整
- 别用：大表全量更新，考虑分批或用临时表替换
- 安全建议：生产环境 UPDATE 前必须先 SELECT 确认，最好开事务

## 3. DELETE 删除数据——橡皮擦，擦掉一行

一句话：DELETE 是按条件删行，TRUNCATE 是直接把表清空——两者区别很大。

**生活比喻**：DELETE 是用橡皮擦挑着擦，TRUNCATE 是把整张纸撕了重铺。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：忘了 WHERE，全表删光
DELETE FROM students;

-- ✅ 好的写法：WHERE 精确限定
DELETE FROM students WHERE student_id = 999;
```

**运行结果：**

```text
执行成功，影响0行（student_id=999不存在，无记录被删除）
```

### 案例1（基础）：条件删除

```sql
-- 删除指定条件的数据
DELETE FROM scores WHERE score < 30;

-- 删除指定学生的所有成绩
DELETE FROM scores WHERE student_id = 3;
```

**运行结果：**

```text
执行成功，影响0行（无符合条件的记录被删除）
```

### 案例2（进阶）：DELETE 与 TRUNCATE 的区别

```sql
-- DELETE：逐行删除，可以回滚，可以有 WHERE
DELETE FROM scores WHERE score IS NULL;

-- TRUNCATE：整表清空，不可回滚，速度极快
TRUNCATE TABLE scores_backup;

-- TRUNCATE vs DELETE 核心区别：
-- 1. TRUNCATE 不走事务日志，速度飞快
-- 2. TRUNCATE 不能回滚（DELETE 可以）
-- 3. TRUNCATE 重置自增ID
-- 4. TRUNCATE 不能加 WHERE 条件
-- 结论：清整表用 TRUNCATE，精确删用 DELETE
```

**运行结果：**

```text
DELETE 执行成功，影响0行
TRUNCATE TABLE 执行成功，scores_backup 表已清空
```

**新手常见坑**：
- **最致命的坑**：DELETE 不写 WHERE，全表数据瞬间清空，想哭都来不及
- 外键约束报错：删主表记录时，从表还有关联数据，会报错删不掉
- 误删重要数据：删错了没备份，只能找 DBA 恢复（如果有的话）
- TRUNCATE 误用：以为 TRUNCATE 能回滚，结果发现回不来了
- 大表 DELETE 卡死：删几百万条数据，事务日志爆满

**面试高频题**：
- DELETE、TRUNCATE、DROP 有啥区别？
- 为什么大表删除要用 TRUNCATE 而不是 DELETE？
- DELETE 能回滚吗？TRUNCATE 能回滚吗？
- 如何安全删除数据？（先 SELECT 确认、开事务、备份）

**什么时候用/什么时候别用**：
- 用：清理脏数据、删除过期记录、数据归档前清理
- 别用：大表批量删除，考虑分批 DELETE 或直接 TRUNCATE
- 安全建议：永远先 SELECT 确认再 DELETE，生产环境必须开事务

## 4. CREATE TABLE 与数据类型——画表格先画格子

一句话：建表就是定义"格子"长什么样——每列叫啥、存什么类型的数据、占多大空间。

**生活比喻**：就像设计一个 Excel 表头，先定义好每列的格式：这列写日期、那列写数字、这列最多20个字。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：全用 VARCHAR，类型不精确
CREATE TABLE bad_students (
    info VARCHAR(255)  -- 啥都往里塞，后期没法计算
);

-- ✅ 好的写法：类型精准，注释清晰
CREATE TABLE good_students (
    student_id INT PRIMARY KEY AUTO_INCREMENT COMMENT '学号',
    name VARCHAR(50) NOT NULL COMMENT '姓名',
    birth_date DATE COMMENT '出生日期'
);
```

**运行结果：**

```text
表创建成功
```

### 案例1（基础）：常见数据类型一览

```sql
-- INT          整数，如学号、年龄
-- VARCHAR(N)    变长字符串，如姓名、地址
-- DATE          日期，如出生日期
-- DECIMAL(M,D)  精确小数，如成绩、学分
-- TEXT          长文本，如备注
-- DATETIME      日期+时间，如创建时间

-- 实战建表
CREATE TABLE teachers (
    teacher_id   INT PRIMARY KEY AUTO_INCREMENT COMMENT '教师ID',
    name         VARCHAR(50) NOT NULL COMMENT '姓名',
    subject      VARCHAR(30) NOT NULL COMMENT '科目',
    salary       DECIMAL(10,2) COMMENT '月薪',
    hire_date    DATE COMMENT '入职日期',
    bio          TEXT COMMENT '个人简介'
);
```

**运行结果：**

```text
表创建成功
```

### 案例2（进阶）：从已有表创建 + 临时表

```sql
-- CREATE TABLE ... AS SELECT：用查询结果建新表
CREATE TABLE students_class1 AS
SELECT student_id, name, phone
FROM students
WHERE class_name = '高三1班';

-- 临时表：连接断开自动消失，适合中转数据
CREATE TEMPORARY TABLE temp_high_scores AS
SELECT student_id, course_id, score
FROM scores
WHERE score >= 90;
```

**运行结果：**

```text
表创建成功
```

**新手常见坑**：
- 数据类型选错：金额用 FLOAT，精度丢失哭都来不及
- VARCHAR 长度不够：存长文本被截断，数据丢失
- 忘了 NOT NULL：全是 NULL，查询时各种坑
- 主键不自增：手动管理主键，冲突不断
- 注释不写：过半年看表结构，完全不知道每列是啥意思

**面试高频题**：
- CHAR 和 VARCHAR 有啥区别？什么时候用哪个？
- DECIMAL 和 FLOAT 有啥区别？为什么金额要用 DECIMAL？
- DATETIME 和 TIMESTAMP 有啥区别？
- 自增主键用完了怎么办？

**什么时候用/什么时候别用**：
- 用：新项目建表、数据迁移前建表、临时表
- 别用：频繁改表结构，考虑用版本管理工具（如 Flyway）
- 设计建议：建表前先画 ER 图，想清楚字段类型和约束

## 5. 约束——规矩，不守规矩就报错

一句话：约束就是给数据定规矩——主键不能重复、外键必须引用、某些列不能为空，违者直接报错。

**生活比喻**：约束就像班规——迟到扣分、作业必须交、不准抄袭。不守规矩就有后果。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：无约束，脏数据随便进
CREATE TABLE bad_scores (
    score_id INT,
    student_id INT,
    score INT
    -- 没有任何约束，重复的、空的、越界的都能插进去
);

-- ✅ 好的写法：五大约束齐全
CREATE TABLE good_scores (
    score_id INT PRIMARY KEY AUTO_INCREMENT,
    student_id INT NOT NULL,
    score DECIMAL(5,2) CHECK (score >= 0 AND score <= 100),
    FOREIGN KEY (student_id) REFERENCES students(student_id)
);
```

**运行结果：**

```text
表创建成功
```

### 案例1（基础）：五种约束逐一演示

```sql
-- 1. PRIMARY KEY 主键约束：唯一 + 不为空
ALTER TABLE students ADD PRIMARY KEY (student_id);

-- 2. FOREIGN KEY 外键约束：引用另一张表的主键
ALTER TABLE scores
ADD CONSTRAINT fk_student
FOREIGN KEY (student_id) REFERENCES students(student_id);

-- 3. UNIQUE 唯一约束：值不能重复
ALTER TABLE students ADD CONSTRAINT uk_phone UNIQUE (phone);

-- 4. NOT NULL 非空约束：必须有值
ALTER TABLE students MODIFY name VARCHAR(50) NOT NULL;

-- 5. CHECK 约束：值必须满足条件
ALTER TABLE scores ADD CONSTRAINT chk_score CHECK (score >= 0 AND score <= 100);
```

**运行结果：**

```text
执行成功，约束已添加
```

### 案例2（进阶）：外键的级联操作

```sql
-- ON DELETE CASCADE：删除主表记录时，从表关联记录也删
-- ON UPDATE CASCADE：更新主表主键时，从表跟着改

CREATE TABLE score_log (
    log_id INT PRIMARY KEY AUTO_INCREMENT,
    student_id INT NOT NULL,
    course_id INT NOT NULL,
    old_score DECIMAL(5,2),
    new_score DECIMAL(5,2),
    FOREIGN KEY (student_id) REFERENCES students(student_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    FOREIGN KEY (course_id) REFERENCES courses(course_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

-- 级联删除：删除学生时，他的成绩日志也跟着删
-- 不加级联的话，删学生时成绩日志会成为孤儿记录
```

**运行结果：**

```text
表创建成功
```

**新手常见坑**：
- 外键约束报错：插数据时外键值不存在，直接报错
- 级联删除误删数据：删主表记录，从表关联数据全没了，想恢复都难
- 约束太严：开发阶段约束太多，测试数据插不进去
- 约束太松：生产环境脏数据满天飞，后期清洗成本巨大
- CHECK 约束不生效：MySQL 早期版本不支持 CHECK，建了也白建

**面试高频题**：
- 主键和唯一键有啥区别？
- 外键的级联操作有哪些？ON DELETE CASCADE 和 ON DELETE SET NULL 啥区别？
- 为什么有些公司不让用外键？（性能、灵活性、分布式场景）
- NOT NULL 和 DEFAULT 有啥区别？

**什么时候用/什么时候别用**：
- 用：核心业务表、数据质量要求高的场景
- 别用：高频写入表（外键影响性能）、分布式数据库（跨库外键难实现）
- 设计建议：开发阶段约束可以松一点，生产环境必须严

## 6. 索引基础——书的目录，翻得快

一句话：索引就像书的目录——有了目录，查内容快；没目录，只能一页一页翻（全表扫描）。

**生活比喻**：索引 = 书的目录。找第5章直接翻目录，不用从第1页逐页找。但索引占空间，不是越多越好。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：不建索引，大表查询慢成狗
-- 或者：啥字段都建索引，插入变慢

-- ✅ 好的写法：只给常用查询条件建索引
CREATE INDEX idx_class ON students(class_name);
```

**运行结果：**

```text
执行成功，索引 idx_class 已创建
```

### 案例1（基础）：创建索引

```sql
-- 普通索引（B-Tree）
CREATE INDEX idx_class ON students(class_name);

-- 唯一索引：值不能重复
CREATE UNIQUE INDEX idx_phone ON students(phone);

-- 查看表的索引
SHOW INDEX FROM students;

-- 删除索引
DROP INDEX idx_class ON students;
```

**运行结果：**

```text
idx_class 索引创建成功
idx_phone 唯一索引创建成功
DROP INDEX 执行成功，idx_class 已删除
```

### 案例2（进阶）：复合索引 + 索引选择原则

```sql
-- 复合索引：多列组合索引
CREATE INDEX idx_student_course ON scores(student_id, course_id);

-- 复合索引的最左前缀原则：
-- idx_student_course 可以覆盖：WHERE student_id = ?
-- 也可以覆盖：WHERE student_id = ? AND course_id = ?
-- 但不能覆盖：WHERE course_id = ?（跳过了最左列）

-- 索引选择原则：
-- 1. WHERE / JOIN / ORDER BY 常用列才建索引
-- 2. 区分度高的列优先（手机号 > 性别）
-- 3. 频繁更新的列少建索引（插入时要维护索引）
-- 4. 小表不用建索引（全表扫描更快）

-- 用 EXPLAIN 验证索引是否生效
EXPLAIN SELECT * FROM students WHERE class_name = '高三1班';
```

**运行结果：**

```text
idx_student_course 复合索引创建成功
EXPLAIN 输出：type=ref，key=idx_class，索引已生效
```

**新手常见坑**：
- 索引建太多：插入、更新变慢，索引维护成本高
- 索引建太少：查询慢成狗，全表扫描
- 复合索引顺序错：最左前缀原则没搞懂，索引白建
- 索引失效：用函数、隐式转换、LIKE '%xxx'，索引直接失效
- 小表也建索引：几千条数据，全表扫描比走索引还快

**面试高频题**：
- 索引的底层结构是啥？B+ 树有啥特点？
- 什么情况下索引会失效？
- 复合索引的最左前缀原则是啥？
- 聚簇索引和非聚簇索引有啥区别？

**什么时候用/什么时候别用**：
- 用：WHERE、JOIN、ORDER BY 频繁查询的列
- 别用：频繁更新的列、区分度低的列（如性别）、小表
- 优化建议：用 EXPLAIN 验证索引是否生效，定期分析慢查询

## 7. 视图 CREATE VIEW——虚拟表，像电视直播不是录像

一句话：视图是一张"虚拟表"——不存真实数据，每次查视图都是实时查底层表，就像看电视直播而不是录像。

**生活比喻**：视图 = 电视直播。底层表是现场，视图是镜头——换一个角度看同一件事，实时同步。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：视图嵌套视图，性能炸裂
CREATE VIEW v1 AS SELECT ...;
CREATE VIEW v2 AS SELECT ... FROM v1;  -- 嵌套，难维护

-- ✅ 好的写法：简单视图，直接查底层表
CREATE VIEW v_student_scores AS
SELECT s.name, c.course_name, sc.score
FROM students s
JOIN scores sc ON s.student_id = sc.student_id
JOIN courses c ON sc.course_id = c.course_id;
```

**运行结果：**

```text
视图 v_student_scores 创建成功
```

### 案例1（基础）：简单视图

```sql
-- 创建视图：每个学生的平均成绩
CREATE VIEW v_avg_score AS
SELECT student_id, AVG(score) AS avg_score
FROM scores
GROUP BY student_id;

-- 查视图，跟查表一样
SELECT * FROM v_avg_score;

-- 删除视图
DROP VIEW IF EXISTS v_avg_score;
```

**运行结果：**

```text
v_avg_score 视图创建成功

SELECT * FROM v_avg_score 结果：
+------------+-----------+
| student_id | avg_score |
+------------+-----------+
|          1 |     92.00 |
|          2 |     85.00 |
|          3 |     78.00 |
+------------+-----------+

DROP VIEW 执行成功
```

### 案例2（进阶）：WITH CHECK OPTION + 复杂视图

```sql
-- 带检查选项的视图：插入/更新必须满足视图条件
-- 比如只看高三1班的学生
CREATE VIEW v_class1_students AS
SELECT student_id, name, phone
FROM students
WHERE class_name = '高三1班'
WITH CHECK OPTION;
-- 通过此视图插入的学生，class_name 必须是 '高三1班'

-- 复杂视图：多表关联 + 聚合
CREATE VIEW v_student_report AS
SELECT
    s.name,
    s.class_name,
    c.course_name,
    sc.score,
    CASE WHEN sc.score >= 90 THEN '优秀'
         WHEN sc.score >= 60 THEN '及格'
         ELSE '不及格'
    END AS grade_level
FROM students s
JOIN scores sc ON s.student_id = sc.student_id
JOIN courses c ON sc.course_id = c.course_id;

-- 查视图
SELECT * FROM v_student_report WHERE grade_level = '优秀';
```

**运行结果：**

```text
v_class1_students 视图创建成功
v_student_report 视图创建成功

SELECT * FROM v_student_report WHERE grade_level = '优秀' 结果：
+------+------------+------------+-------+-------------+
| name | class_name | course_name| score | grade_level |
+------+------------+------------+-------+-------------+
| 张三 | 高三A班    | 数学       | 92.00 | 优秀        |
+------+------------+------------+-------+-------------+
```

**新手常见坑**：
- 视图套视图：性能炸裂，维护困难
- 视图里用聚合：不能直接更新，只能查
- 视图依赖底层表：底层表结构改了，视图直接报错
- 复杂视图查询慢：每次查视图都是实时查底层表，复杂视图性能差
- 以为视图存数据：视图是虚拟表，不存数据，每次都是实时查询

**面试高频题**：
- 视图和表有啥区别？
- 视图能更新吗？什么情况下不能更新？
- 视图的优缺点是啥？
- 什么时候用视图，什么时候用物化视图？

**什么时候用/什么时候别用**：
- 用：简化复杂查询、权限控制（只暴露部分列）、统一数据口径
- 别用：高频查询的复杂聚合（考虑物化视图或定时任务）、视图套视图
- 设计建议：视图保持简单，避免嵌套，定期检查视图性能

## 8. 事务基础——一揽子买卖，要么全干要么全不干

一句话：事务把多条 SQL 捆成一揽子买卖——全成功才提交，有一条失败就全部回滚，保证数据不丢不乱。

**生活比喻**：事务 = 银行转账。张三给李四转100块——扣钱和加钱必须同时成功，不能扣了钱却没加上，那叫"数据事故"。

### 好的写法 vs 不好的写法

```sql
-- ❌ 不好的写法：转账只做一半，中途出错钱就丢了
UPDATE accounts SET balance = balance - 100 WHERE name = '张三';
-- 这里如果出错，李四没加钱，张三钱扣了

-- ✅ 好的写法：事务包裹，要么全成功要么全回滚
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE name = '张三';
UPDATE accounts SET balance = balance + 100 WHERE name = '李四';
COMMIT;
```

**运行结果：**

```text
START TRANSACTION 已开始
UPDATE 执行成功，影响1行
UPDATE 执行成功，影响1行
COMMIT 已提交
```

### 案例1（基础）：事务的 ACID + BEGIN/COMMIT/ROLLBACK

```sql
-- 事务四大特性 ACID：
-- A 原子性：全成功或全失败
-- C 一致性：数据从一个一致状态到另一个一致状态
-- I 隔离性：事务之间互不干扰
-- D 持久性：提交后数据永久保存

-- 基本事务
START TRANSACTION;  -- 或 BEGIN

-- 删除学生时，先删成绩再删学生（外键约束）
DELETE FROM scores WHERE student_id = 2;
DELETE FROM students WHERE student_id = 2;

COMMIT;  -- 全部成功，提交

-- 如果中途出错：
-- ROLLBACK;  -- 回滚，恢复原样
```

**运行结果：**

```text
START TRANSACTION 已开始
DELETE 执行成功，影响2行
DELETE 执行成功，影响1行
COMMIT 已提交
```

### 案例2（进阶）：SAVEPOINT 保存点 + 事务实战

```sql
-- SAVEPOINT：事务里的"检查点"，可以部分回滚
START TRANSACTION;

-- 第一步：更新成绩
UPDATE scores SET score = 95 WHERE student_id = 1 AND course_id = 1;
SAVEPOINT sp1;  -- 保存点1

-- 第二步：再更新另一个
UPDATE scores SET score = 88 WHERE student_id = 1 AND course_id = 2;
SAVEPOINT sp2;  -- 保存点2

-- 第三步：有问题，回滚到保存点2
-- ROLLBACK TO sp2;  -- 只回滚 sp2 之后的操作

-- 全部成功则提交
COMMIT;

-- =============================================
-- 事务实战：批量录入成绩，失败则全部回滚
-- =============================================
START TRANSACTION;

INSERT INTO scores (student_id, course_id, score, exam_date)
VALUES (1, 1, 92, '2025-06-01');

INSERT INTO scores (student_id, course_id, score, exam_date)
VALUES (2, 1, 85, '2025-06-01');

INSERT INTO scores (student_id, course_id, score, exam_date)
VALUES (3, 1, 78, '2025-06-01');

-- 如果任何一条失败，上面三条全部回滚
COMMIT;
```

**运行结果：**

```text
START TRANSACTION 已开始
UPDATE 执行成功，影响1行
SAVEPOINT sp1 已设置
UPDATE 执行成功，影响1行
SAVEPOINT sp2 已设置
COMMIT 已提交

批量录入事务：
START TRANSACTION 已开始
INSERT 执行成功，影响1行
INSERT 执行成功，影响1行
INSERT 执行成功，影响1行
COMMIT 已提交
```

**新手常见坑**：
- **最致命的坑**：事务开了不提交（COMMIT），数据改了但不生效，排查半天
- 事务开了不回滚（ROLLBACK）：出错不回滚，数据状态不一致
- 长事务：事务时间太长，锁表太久，其他操作全堵住
- 死锁：两个事务互相等对方释放锁，直接卡死
- 忘了设置隔离级别：脏读、幻读、不可重复读各种问题

**面试高频题**：
- 事务的 ACID 特性是啥？分别解决什么问题？
- 事务的隔离级别有哪些？MySQL 默认是哪个？
- 什么是脏读、幻读、不可重复读？
- 死锁怎么解决？怎么避免？

**什么时候用/什么时候别用**：
- 用：转账、订单创建、批量操作、需要原子性的场景
- 别用：长事务（考虑拆分）、高并发场景（考虑乐观锁）
- 最佳实践：事务尽量短，及时 COMMIT 或 ROLLBACK，避免长事务

## 实战案例：数据迁移、数据清洗、数据归档

### 案例1：批量数据导入——从 Excel 导入 10 万条学生数据

**场景**：学校新学期开学，需要从 Excel 导入 10 万条新生数据到 students 表。

**错误做法**（一条条循环插）：
```sql
-- ❌ 性能极差，10 万条要跑几小时
INSERT INTO students (name, gender, birth_date, class_name, phone) VALUES ('学生1', '男', '2008-01-01', '高一1班', '13800000001');
INSERT INTO students (name, gender, birth_date, class_name, phone) VALUES ('学生2', '男', '2008-01-02', '高一1班', '13800000002');
-- ... 循环 10 万次
```

**正确做法**（批量插入 + 事务）：
```sql
-- ✅ 方案1：批量插入，每批 1000 条
START TRANSACTION;
INSERT INTO students (name, gender, birth_date, class_name, phone) VALUES
    ('学生1', '男', '2008-01-01', '高一1班', '13800000001'),
    ('学生2', '男', '2008-01-02', '高一1班', '13800000002'),
    -- ... 每批 1000 条
    ('学生1000', '男', '2008-01-01', '高一1班', '13800001000');
COMMIT;

-- ✅ 方案2：LOAD DATA INFILE（最快，适合超大数据量）
-- 先把 Excel 导出为 CSV，然后用 LOAD DATA 导入
LOAD DATA INFILE '/tmp/students.csv'
INTO TABLE students
FIELDS TERMINATED BY ','
LINES TERMINATED BY '\n'
IGNORE 1 LINES  -- 跳过 CSV 表头
(name, gender, birth_date, class_name, phone);
```

**数据安全提醒**：
- 导入前先备份原表：`CREATE TABLE students_backup AS SELECT * FROM students;`
- 用事务包裹，失败可以回滚
- 导入后验证数据量：`SELECT COUNT(*) FROM students;`

### 案例2：数据修正——批量修正成绩录入错误

**场景**：老师发现数学成绩录入时多加了 10 分，需要批量修正。

**错误做法**（直接 UPDATE）：
```sql
-- ❌ 没确认影响范围，可能改错数据
UPDATE scores SET score = score - 10 WHERE course_id = 1;
```

**正确做法**（先 SELECT 确认 + 事务 + 备份）：
```sql
-- 第一步：先备份受影响的数据
CREATE TABLE scores_fix_backup AS
SELECT * FROM scores WHERE course_id = 1;

-- 第二步：先 SELECT 确认影响范围
SELECT student_id, score, score - 10 AS new_score
FROM scores
WHERE course_id = 1;

-- 第三步：开事务修正
START TRANSACTION;
UPDATE scores SET score = score - 10 WHERE course_id = 1;

-- 第四步：验证修正结果
SELECT student_id, score FROM scores WHERE course_id = 1 LIMIT 10;

-- 第五步：确认无误后提交
COMMIT;
-- 如果有问题，ROLLBACK;
```

**数据安全提醒**：
- 永远先 SELECT 确认影响范围
- 修正前必须备份
- 用事务包裹，可以回滚
- 修正后验证结果

### 案例3：数据归档——把 3 年前的成绩数据归档到历史表

**场景**：成绩表数据量太大，需要把 3 年前的数据归档到历史表，减轻主表压力。

**步骤**：
```sql
-- 第一步：创建历史表（结构和主表一致）
CREATE TABLE scores_history LIKE scores;

-- 第二步：查询要归档的数据量
SELECT COUNT(*) FROM scores WHERE exam_date < '2022-01-01';

-- 第三步：开事务，先插入历史表，再删除主表
START TRANSACTION;

-- 插入历史表
INSERT INTO scores_history
SELECT * FROM scores WHERE exam_date < '2022-01-01';

-- 验证插入数量
SELECT COUNT(*) FROM scores_history;

-- 删除主表数据
DELETE FROM scores WHERE exam_date < '2022-01-01';

-- 验证删除数量
SELECT COUNT(*) FROM scores WHERE exam_date < '2022-01-01';

-- 确认无误后提交
COMMIT;

-- 第四步：优化主表（释放空间）
OPTIMIZE TABLE scores;
```

**数据安全提醒**：
- 归档前先备份
- 先插入历史表，再删除主表，避免数据丢失
- 用事务保证原子性
- 归档后验证数据完整性

## 数据操作安全建议（必读）

### 1. UPDATE/DELETE 前必须做的事
```sql
-- ✅ 标准流程
-- 1. 先 SELECT 确认影响范围
SELECT * FROM students WHERE class_name = '高三1班';

-- 2. 备份受影响的数据
CREATE TABLE students_backup_20250521 AS
SELECT * FROM students WHERE class_name = '高三1班';

-- 3. 开事务执行
START TRANSACTION;
UPDATE students SET class_name = '高三A班' WHERE class_name = '高三1班';

-- 4. 验证结果
SELECT * FROM students WHERE class_name = '高三A班';

-- 5. 确认无误后提交
COMMIT;
```

### 2. 批量操作的最佳实践
- **分批处理**：大批量操作分批执行，避免锁表太久
- **事务控制**：每批用事务包裹，失败可以回滚
- **监控进度**：记录已处理的行数，方便断点续传
- **错峰执行**：大操作在业务低峰期执行

### 3. 数据备份策略
- **操作前备份**：任何可能修改数据的操作前，先备份
- **定期全量备份**：每天全量备份，每小时增量备份
- **备份验证**：定期验证备份是否可恢复
- **多地备份**：本地 + 远程 + 云存储

### 4. 生产环境红线
- **永远不要**：不带 WHERE 的 UPDATE/DELETE
- **永远不要**：不开事务的批量操作
- **永远不要**：不备份的直接操作
- **永远不要**：业务高峰期的大批量操作

## 知识点速查表

| 操作 | 一句话 | 核心语法 | 常见坑 |
|------|--------|----------|--------|
| INSERT | 往表里塞数据 | `INSERT INTO t (cols) VALUES (vals)` | 列名顺序错、主键冲突、批量插到一半失败 |
| UPDATE | 改已有数据 | `UPDATE t SET col=val WHERE ...` | **不写 WHERE 全表改**、子查询性能差、CASE 忘了 ELSE |
| DELETE | 删数据 | `DELETE FROM t WHERE ...` | **不写 WHERE 全表删**、外键约束报错、大表 DELETE 卡死 |
| TRUNCATE | 清空整表 | `TRUNCATE TABLE t` | **不能回滚**、重置自增 ID、误删无法恢复 |
| CREATE TABLE | 建表 | `CREATE TABLE t (col type, ...)` | 数据类型选错、VARCHAR 长度不够、忘了 NOT NULL |
| 约束 | 数据规矩 | `PRIMARY KEY / FOREIGN KEY / UNIQUE / NOT NULL / CHECK` | 外键报错、级联误删、约束太严或太松 |
| 索引 | 查询加速 | `CREATE INDEX idx ON t(col)` | 建太多、建太少、复合索引顺序错、索引失效 |
| 视图 | 虚拟表 | `CREATE VIEW v AS SELECT ...` | 视图套视图、聚合视图不能更新、依赖底层表 |
| 事务 | 一揽子操作 | `START TRANSACTION; ... COMMIT;` | **开了不提交**、长事务、死锁、隔离级别问题 |
