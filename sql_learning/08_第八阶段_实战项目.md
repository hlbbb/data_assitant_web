## 项目1：电商用户行为分析

### 业务背景

你刚入职一家电商公司做数据分析师。某天，运营总监拿着一叠报表冲进会议室："咱们平台流量不小，但转化率一直上不去，老板让我下周汇报问题出在哪。你给我分析一下，用户从进来到下单，到底在哪个环节流失了？"

这是一个典型的电商难题：**用户来得多，买的少**。你需要搞清楚：
1. 用户从浏览到支付，每一步流失了多少人？
2. 用户买几次？是一次性客户还是回头客？
3. 每个用户平均花了多少钱？
4. 复购率是多少？

### 完整SQL

#### 1. 漏斗分析

```sql
-- 漏斗分析:统计每个环节的用户数
SELECT
    '浏览' AS step_name,
    COUNT(DISTINCT user_id) AS user_count
FROM user_behavior
WHERE behavior_type = 'browse'

UNION ALL

SELECT
    '加购' AS step_name,
    COUNT(DISTINCT user_id) AS user_count
FROM user_behavior
WHERE behavior_type = 'cart'

UNION ALL

SELECT
    '下单' AS step_name,
    COUNT(DISTINCT user_id) AS user_count
FROM user_behavior
WHERE behavior_type = 'order'

UNION ALL

SELECT
    '支付' AS step_name,
    COUNT(DISTINCT user_id) AS user_count
FROM user_behavior
WHERE behavior_type = 'pay'
ORDER BY user_count DESC;
```

**运行结果:**

```text
+-----------+------------+
| step_name | user_count |
+-----------+------------+
| 浏览      |         20 |
| 加购      |         13 |
| 下单      |         12 |
| 支付      |         10 |
+-----------+------------+
```

#### 2. 用户购买频次分布

```sql
-- 购买频次:按用户统计支付次数,看分布
SELECT
    pay_count AS purchase_times,
    COUNT(*) AS user_count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) AS pct
FROM (
    SELECT user_id, COUNT(*) AS pay_count
    FROM user_behavior
    WHERE behavior_type = 'pay'
    GROUP BY user_id
) t
GROUP BY pay_count
ORDER BY pay_count;
```

**运行结果:**

```text
+-----------------+------------+--------+
| purchase_times  | user_count | pct    |
+-----------------+------------+--------+
|               1 |          8 |  80.00 |
|               2 |          2 |  20.00 |
+-----------------+------------+--------+
```

#### 3. 客单价分析

```sql
-- 客单价:每个付费用户的支付次数统计
-- 注意:user_behavior 表没有金额字段,这里用支付次数代替
-- 实际业务中通常从订单表获取金额数据
SELECT
    AVG(pay_count) AS avg_pay_times,
    MAX(pay_count) AS max_pay_times,
    MIN(pay_count) AS min_pay_times
FROM (
    SELECT user_id, COUNT(*) AS pay_count
    FROM user_behavior
    WHERE behavior_type = 'pay'
    GROUP BY user_id
) t;
```

**运行结果:**

```text
+---------------+-----------------+-----------------+
| avg_pay_times | max_pay_times   | min_pay_times   |
+---------------+-----------------+-----------------+
|        1.2000 |               2 |               1 |
+---------------+-----------------+-----------------+
```

#### 4. 复购率

```sql
-- 复购率:支付2次及以上的用户占比
SELECT
    COUNT(*) AS total_pay_users,
    SUM(CASE WHEN pay_count >= 2 THEN 1 ELSE 0 END) AS repeat_users,
    ROUND(SUM(CASE WHEN pay_count >= 2 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS repeat_rate
FROM (
    SELECT user_id, COUNT(*) AS pay_count
    FROM user_behavior
    WHERE behavior_type = 'pay'
    GROUP BY user_id
) t;
```

**运行结果:**

```text
+-----------------+--------------+-------------+
| total_pay_users | repeat_users | repeat_rate |
+-----------------+--------------+-------------+
|              10 |            2 |       20.00 |
+-----------------+--------------+-------------+
```

### 结果解读

- **漏斗**:从浏览到支付,每一步都有流失。加购→下单、下单→支付是关键转化点,这两步流失多说明商品定价或支付流程有问题。
- **购买频次**:大部分用户只买1次,少数用户买2次以上。
- **客单价**:由于行为表没有金额字段,这里用支付次数代替。实际业务中应关联订单表计算真实客单价。
- **复购率**:复购率低说明用户粘性差,需要运营手段提升。

**教学点 #1**:漏斗分析的核心是 COUNT(DISTINCT user_id),每一步都要去重,因为一个用户可能多次浏览。

**教学点 #2**:复购率 = 复购用户 / 总付费用户,是衡量用户粘性的关键指标。

### 新手常见坑

**坑点1:忘记去重**
```sql
-- 错误写法
SELECT COUNT(user_id) FROM user_behavior WHERE behavior_type = 'browse'
-- 一个用户浏览了10次,会被算成10个人

-- 正确写法
SELECT COUNT(DISTINCT user_id) FROM user_behavior WHERE behavior_type = 'browse'
```

**坑点2:漏斗步骤理解错误**
- 漏斗不是简单的"必须按顺序来",用户可能直接下单不浏览(比如从搜索结果进来的)
- 实际业务中,漏斗分析要结合业务场景定义

**坑点3:复购率计算出错**
```sql
-- 错误:分母用了所有用户,而不是付费用户
SELECT SUM(CASE WHEN pay_count >= 2 THEN 1 ELSE 0 END) / COUNT(*)
FROM (SELECT user_id, COUNT(*) AS pay_count FROM user_behavior GROUP BY user_id) t

-- 正确:分母是付费用户
SELECT SUM(CASE WHEN pay_count >= 2 THEN 1 ELSE 0 END) / COUNT(*)
FROM (
    SELECT user_id, COUNT(*) AS pay_count
    FROM user_behavior
    WHERE behavior_type = 'pay'
    GROUP BY user_id
) t
```

**坑点4:数据量不足导致结论不可信**
- 示例数据只有20个用户,实际业务中至少要几千到几万样本
- 小样本的漏斗分析可能受个别用户影响,要结合时间维度看趋势

## 项目2:财务月报生成

### 业务背景

月底了,财务经理找到你:"每个月我都得手工做报表,又是Excel又是计算器,太累了。你能不能帮我写个SQL,一键出月报?"

老板要看的内容:
1. 每月的收入、支出、净利润
2. 同比(和去年同月比)和环比(和上月比)
3. 各部门费用占比
4. 预算执行率(花了多少 / 预算多少)

这是典型的财务自动化场景,也是SQL在财务领域最常见的应用之一。

### 分析价值

**直接价值**:
- 节省财务人员50%以上的手工统计时间
- 减少人为计算错误
- 支持多维度分析(按部门、按科目、按时间)

**间接价值**:
- 建立财务数据的标准分析框架
- 为预算编制和成本控制提供数据支撑
- 支持管理层决策(比如哪个部门超预算了)

### 分析思路

1. 收入支出按月汇总
2. 用自连接算同比环比
3. 部门费用用 GROUP BY + 占比
4. 预算执行率用实际 / 预算

### 完整SQL

#### 1. 月度收入支出汇总

```sql
-- 月度汇总:收入、支出、净利润
SELECT
    DATE_FORMAT(record_date, '%Y-%m') AS month,
    SUM(CASE WHEN category = 'income' THEN amount ELSE 0 END) AS total_income,
    SUM(CASE WHEN category = 'expense' THEN amount ELSE 0 END) AS total_expense,
    SUM(CASE WHEN category = 'income' THEN amount ELSE 0 END) -
    SUM(CASE WHEN category = 'expense' THEN amount ELSE 0 END) AS net_profit
FROM finance_records
GROUP BY DATE_FORMAT(record_date, '%Y-%m')
ORDER BY month;
```

#### 2. 同比环比

```sql
-- 同比环比:用CTE + 自连接
WITH monthly AS (
    SELECT
        DATE_FORMAT(record_date, '%Y-%m') AS month,
        SUM(CASE WHEN category = 'income' THEN amount ELSE 0 END) AS income,
        SUM(CASE WHEN category = 'expense' THEN amount ELSE 0 END) AS expense
    FROM finance_records
    GROUP BY DATE_FORMAT(record_date, '%Y-%m')
),
with_prev AS (
    SELECT
        m.month,
        m.income,
        m.expense,
        LAG(m.income) OVER (ORDER BY m.month) AS prev_income,
        LAG(m.expense) OVER (ORDER BY m.month) AS prev_expense
    FROM monthly m
)
SELECT
    month,
```

## 项目3:留存率分析

### 业务背景

你负责一款APP的用户增长。产品经理跑来问你:"我们每天新增不少用户,但他们能留下多少?老板让我分析一下用户粘性,看看我们的产品是不是有吸引力。"

这是互联网产品的核心问题:**拉新容易留存难**。你需要回答:
1. 新用户第二天还来的有多少?(次日留存)
2. 7天后还有多少?(7日留存)
3. 30天后还有多少?(30日留存)
4. 不同渠道的留存率差别大吗?

### 分析价值

**直接价值**:
- 评估产品粘性:留存率高说明产品有价值,留存率低要找原因
- 评估渠道质量:不同渠道拉来的用户质量不同,留存率能暴露问题
- 指导运营策略:如果7日留存高但30日留存低,说明中期运营不够

**间接价值**:
- 建立用户生命周期模型
- 预测用户价值(LTV)
- 为产品迭代提供方向

### 分析思路

1. 找出每个用户的首次活跃日期(注册日)
2. 计算每次活跃距首次的天数差
3. 按天数差统计留存人数
4. 留存率 = 留存人数 / 新增人数

### 完整SQL

#### 1. 次日/7日/30日留存

```sql
-- 留存率分析
-- Step1: 每个用户的首次活跃日期
-- Step2: 计算每次活跃距首次的天数差
-- Step3: 统计留存

WITH first_activity AS (
    -- 每个用户首次活跃的日期
    SELECT user_id, MIN(activity_date) AS first_date
    FROM user_activity
    GROUP BY user_id
),
retention_data AS (
    -- 每次活跃距首次的天数差
    SELECT
        fa.first_date,
        ua.activity_date,
        DATEDIFF(ua.activity_date, fa.first_date) AS day_diff
    FROM user_activity ua
    JOIN first_activity fa ON ua.user_id = fa.user_id
)
SELECT
    first_date AS cohort_date,
    COUNT(DISTINCT CASE WHEN day_diff = 0 THEN first_date END) AS new_users,
    COUNT(DISTINCT CASE WHEN day_diff = 1 THEN first_date END) AS day1_retained,
    COUNT(DISTINCT CASE WHEN day_diff = 7 THEN first_date END) AS day7_retained,
    COUNT(DISTINCT CASE WHEN day_diff = 30 THEN first_date END) AS day30_retained,
    -- 留存人数 / 新增人数(近似:用总新增用户数)
    ROUND(COUNT(DISTINCT CASE WHEN day_diff = 1 THEN first_date END) * 100.0 /
          NULLIF(COUNT(DISTINCT CASE WHEN day_diff = 0 THEN first_date END), 0), 2) AS day1_rate,
    ROUND(COUNT(DISTINCT CASE WHEN day_diff = 7 THEN first_date END) * 100.0 /
          NULLIF(COUNT(DISTINCT CASE WHEN day_diff = 0 THEN first_date END), 0), 2) AS day7_rate,
    ROUND(COUNT(DISTINCT CASE WHEN day_diff = 30 THEN first_date END) * 100.0 /
          NULLIF(COUNT(DISTINCT CASE WHEN day_diff = 0 THEN first_date END), 0), 2) AS day30_rate
FROM retention_data
GROUP BY first_date
ORDER BY first_date;
```

> 注意:上面的简化写法中,`COUNT(DISTINCT CASE WHEN day_diff = 0 THEN first_date END)` 对每个 cohort 只会返回 1(因为 first_date 值相同),导致 new_users 始终为 1,留存率总是 100%。这是简化写法的缺陷,请看下面精确写法的结果。

> 注意:上面的写法有简化。更精确的做法是先算出每个cohort的新增用户数,再算留存。下面是精确写法:

```sql
-- 精确留存率(先算新增,再算留存)
WITH first_activity AS (
    SELECT user_id, MIN(activity_date) AS first_date
    FROM user_activity
    GROUP BY user_id
),
new_users_count AS (
    SELECT first_date, COUNT(*) AS new_user_count
    FROM first_activity
    GROUP BY first_date
),
retention AS (
    SELECT
        fa.first_date,
        DATEDIFF(ua.activity_date, fa.first_date) AS day_diff
    FROM user_activity ua
    JOIN first_activity fa ON ua.user_id = fa.user_id
)
SELECT
    n.first_date AS cohort_date,
    n.new_user_count,
    COALESCE(SUM(CASE WHEN r.day_diff = 1 THEN 1 ELSE 0 END), 0) AS day1_retained,
    COALESCE(SUM(CASE WHEN r.day_diff = 7 THEN 1 ELSE 0 END), 0) AS day7_retained,
    COALESCE(SUM(CASE WHEN r.day_diff = 30 THEN 1 ELSE 0 END), 0) AS day30_retained,
    ROUND(COALESCE(SUM(CASE WHEN r.day_diff = 1 THEN 1 ELSE 0 END), 0) * 100.0 / n.new_user_count, 2) AS day1_rate,
    ROUND(COALESCE(SUM(CASE WHEN r.day_diff = 7 THEN 1 ELSE 0 END), 0) * 100.0 / n.new_user_count, 2) AS day7_rate,
    ROUND(COALESCE(SUM(CASE WHEN r.day_diff = 30 THEN 1 ELSE 0 END), 0) * 100.0 / n.new_user_count, 2) AS day30_rate
FROM new_users_count n
LEFT JOIN retention r ON n.first_date = r.first_date AND r.day_diff > 0
GROUP BY n.first_date, n.new_user_count
ORDER BY n.first_date;
```

```text
| cohort_date | new_user_count| day1_retained | day7_retained | day30_retained | day1_rate | day7_rate | day30_rate |
+-------------+---------------+---------------+---------------+----------------+-----------+-----------+------------+
| 2026-04-01  |             5 |             2 |             1 |              1 |     40.00 |     20.00 |      20.00 |
| 2026-04-02  |             5 |             2 |             1 |              1 |     40.00 |     20.00 |      20.00 |
| 2026-04-03  |             5 |             3 |             1 |              0 |     60.00 |     20.00 |       0.00 |
| 2026-04-04  |             5 |             3 |             0 |              1 |     60.00 |      0.00 |      20.00 |
| 2026-04-05  |             5 |             3 |             1 |              1 |     60.00 |     20.00 |      20.00 |
```

#### 2. 按渠道分析留存

```sql
-- 按渠道的留存率
WITH first_activity AS (
    SELECT user_id, MIN(activity_date) AS first_date,
           MIN(channel) AS channel  -- 首次渠道
    FROM user_activity
    GROUP BY user_id

channel_retention AS (

        fa.channel,
        DATEDIFF(ua.activity_date, fa.first_date) AS day_diff
    FROM user_activity ua
    JOIN first_activity fa ON ua.user_id = fa.user_id
)
SELECT
    fa.channel,
    COUNT(*) AS new_users,
    SUM(CASE WHEN cr.day_diff = 1 THEN 1 ELSE 0 END) AS day1,
    SUM(CASE WHEN cr.day_diff = 7 THEN 1 ELSE 0 END) AS day7,
    ROUND(SUM(CASE WHEN cr.day_diff = 1 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS day1_rate,
    ROUND(SUM(CASE WHEN cr.day_diff = 7 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS day7_rate
FROM first_activity fa
LEFT JOIN channel_retention cr ON fa.channel = cr.channel AND cr.day_diff > 0
GROUP BY fa.channel;
```

```sql
    FROM user_activity

weekly_cohort AS (

),
retention_calc AS (

        DATEDIFF(ua.activity_date, fa.first_date) AS day_diff
    FROM user_activity ua
    JOIN first_activity fa ON ua.user_id = fa.user_id
)
SELECT
    wc.cohort_week,
    wc.new_users,
    COALESCE(SUM(CASE WHEN rc.day_diff = 1 THEN 1 ELSE 0 END), 0) AS day1,
    COALESCE(SUM(CASE WHEN rc.day_diff = 7 THEN 1 ELSE 0 END), 0) AS day7
FROM weekly_cohort wc
LEFT JOIN retention_calc rc ON DATE_FORMAT(rc.first_date, '%Y-%U') = wc.cohort_week
GROUP BY wc.cohort_week, wc.new_users
ORDER BY wc.cohort_week;
```

### 结果解读

- **次日留存**:用户注册后第二天回来的比例,>40%算优秀。
- **7日留存**:一周后还回来的,>20%算合格。
- **30日留存**:一个月后还回来的,>10%算合格。
- **渠道差异**:付费渠道可能留存低(用户只是被广告拉来的),自然渠道可能留存高。

**教学点 #6**:留存分析的核心是"首次日期 + 天数差"——先找首次活跃日,再算每次活跃距首次多少天。

**教学点 #7**:留存率 = 留存人数 / 新增人数,分子分母必须对齐。

**教学点 #8**:按渠道看留存,能发现哪些渠道拉来的用户质量高。

### 新手常见坑

**坑点1:留存率计算时分子分母不对齐**
```sql
-- 错误:分母是所有活跃用户,分子是某天活跃用户
SELECT
    COUNT(DISTINCT CASE WHEN day_diff = 1 THEN user_id END) /
    COUNT(DISTINCT user_id)

-- 正确:分母是该cohort的新增用户
-- 要先确定每个cohort的新增用户数,再算留存
```

**坑点2:忽略第一次活跃日(第0天)**
- 留存分析的"第0天"是注册当天,用户一定在
- 计算留存率时,第0天是分母,第1天才是分子

**坑点3:渠道留存分析关联错误**
- 按渠道分析时,要用用户ID关联,不是用渠道名关联
- 一个用户只有一个首次渠道,不要混淆

**坑点4:数据量不足导致留存率为0**
- 30日留存需要观察30天,早期数据可能不够
- 如果某天的新增用户只有2-3个,留存率波动会很大

### 面试高频题

**Q1:留存率低,怎么分析原因?**

- 看用户行为:高留存用户和低留存用户有什么不同?

**Q2:留存率的行业基准是多少?**

## 项目4:A/B测试分析

### 业务背景

产品经理做了一个新功能(新版首页),想和旧版对比效果。他问你:"我们做了个新版首页,感觉比旧版好看,但老板要数据说话。你帮我做个A/B测试分析,看看新版是不是真的更好?"

这是一个典型的产品决策问题:**凭感觉不够,要凭数据**。你需要回答:
1. 新版和旧版各有多少人?转化率分别是多少?
2. 转化率差异是否显著?还是只是随机波动?
3. 95%置信度下,差异是否可信?

### 分析价值

**直接价值**:
- 用数据验证产品假设,避免拍脑袋决策
- 量化改版效果,知道投入产出比
- 降低产品迭代风险

**间接价值**:
- 建立数据驱动的产品文化
- 积累A/B测试方法论
- 为后续测试提供参考

### 分析思路

1. 统计每组的用户数和转化数
2. 计算转化率
3. 用SQL实现统计检验(z检验)
4. 判断显著性

#### 2. 转化率计算 + 显著性检验

```sql
-- A/B测试统计检验(z检验)
-- H0: 两组转化率无差异
-- 用SQL实现

SELECT
    control.total AS control_total,
    treatment.total AS treatment_total,
    control.converted AS control_converted,
    treatment.converted AS treatment_converted,
    ROUND(control.converted * 100.0 / control.total, 2) AS control_rate,
    ROUND(treatment.converted * 100.0 / treatment.total, 2) AS treatment_rate,
    -- z检验
    ROUND(
        (treatment.converted * 1.0 / treatment.total - control.converted * 1.0 / control.total)
        /
        SQRT(
            (control.converted * 1.0 / control.total * (1 - control.converted * 1.0 / control.total) / control.total)
            +
            (treatment.converted * 1.0 / treatment.total * (1 - treatment.converted * 1.0 / treatment.total) / treatment.total)
        )
    , 4) AS z_score,
    CASE
        WHEN ABS(
            (treatment.converted * 1.0 / treatment.total - control.converted * 1.0 / control.total)
            /
            SQRT(
                (control.converted * 1.0 / control.total * (1 - control.converted * 1.0 / control.total) / control.total)
                +
                (treatment.converted * 1.0 / treatment.total * (1 - treatment.converted * 1.0 / treatment.total) / treatment.total)
            )
        ) > 1.96 THEN '显著(95%置信度)'
        ELSE '不显著'
    END AS significance
FROM (
    SELECT
        COUNT(*) AS total,
        SUM(converted) AS converted
    FROM ab_test
    WHERE test_group = 'control'
) control,
(
    SELECT
        COUNT(*) AS total,
        SUM(converted) AS converted
    FROM ab_test
    WHERE test_group = 'treatment'
) treatment;
```

**运行结果:**

```text
+---------------+------------------+---------------------+------------------+----------------+-----------------+---------+--------------+
| control_total | treatment_total  | control_converted   | treatment_converted| control_rate  | treatment_rate  | z_score | significance |
+---------------+------------------+---------------------+-------------------+---------------+-----------------+---------+--------------+
|            15 |               15 |                   6 |                10 |         40.00 |           66.67 |  1.5191 | 不显著       |
+---------------+------------------+---------------------+-------------------+---------------+-----------------+---------+--------------+
```

> 注:z_score = 1.5191 < 1.96,说明在95%置信度下差异不显著。虽然实验组转化率更高(66.67% vs 40.00%),但由于样本量太小(仅15人/组),无法排除随机波动。这也印证了教学点#12:样本量要够大。

#### 3. 多维度A/B对比

```sql
-- 按停留时间和浏览深度分组看转化
SELECT
    test_group,
    CASE
        WHEN time_spent >= 100 THEN '深度用户(>100秒)'
        WHEN time_spent >= 60 THEN '中等用户(60-100秒)'
        ELSE '浅层用户(<60秒)'
    END AS user_depth,
    COUNT(*) AS users,
    SUM(converted) AS conversions,
    ROUND(SUM(converted) * 100.0 / COUNT(*), 2) AS conv_rate
FROM ab_test
GROUP BY test_group,
    CASE
        WHEN time_spent >= 100 THEN '深度用户(>100秒)'
        WHEN time_spent >= 60 THEN '中等用户(60-100秒)'
        ELSE '浅层用户(<60秒)'
    END
ORDER BY test_group, user_depth;
```

**运行结果:**

```text

| test_group  | user_depth                | users | conversions | conv_rate |

| control     | 浅层用户(<60秒)          |     9 |           0 |      0.00 |
| control     | 深度用户(>100秒)         |     2 |           2 |    100.00 |
| control     | 中等用户(60-100秒)       |     4 |           4 |    100.00 |

+-------------+---------------------------+-------+-------------+-----------+
```

### 结果解读

- **转化率差异**:实验组转化率明显高于对照组,说明新版首页有效。
- **z检验**:z值>1.96说明差异在95%置信度下显著,不是随机波动。
- **深度用户**:停留时间长的用户转化率更高,符合直觉。

**教学点 #9**:A/B测试的关键是两组对比——控制变量,只改一个因素。

**教学点 #10**:z检验的z值>1.96 = 95%显著。z值>2.576 = 99%显著。这是统计学基础。

**教学点 #11**:SQL可以做统计检验,虽然不如Python/R灵活,但适合大规模数据和自动化报表。

**教学点 #12**:A/B测试的样本量要够——每组至少几百到几千,30条数据只是演示用。

### 新手常见坑

**坑点1:样本量不足**
- 例子中只有15人/组,实际业务中至少要几百到几千
- 样本量小会导致差异"不显著",即使实际有差异
- 在做A/B测试前,先算样本量(用样本量计算器)

**坑点2:多变量干扰**
- A/B测试要控制变量,只改一个因素
- 如果同时改了首页、价格、支付流程,就无法判断哪个起作用

**坑点3:统计显著性 vs 业务显著性**
- 统计显著不一定有业务价值
- 比如转化率从40%提升到40.1%,统计显著,但业务价值很小

**坑点4:忽略分组偏差**
- 如果对照组和实验组的用户特征分布不同,结果可能失真
- 检查两组的性别、年龄、地域分布是否均衡

### 面试高频题

**Q1:A/B测试结果不显著,怎么办?**
- 增加样本量:延长测试时间或扩大流量
- 检查实验设计:是否有干扰因素
- 分层分析:可能在某个用户群体中显著
- 调整显著性水平:从95%降到90%

**Q2:如何确定A/B测试的样本量?**
- 根据预期提升幅度、基线转化率、显著性水平计算
- 用样本量计算器或Python的statsmodels库
- 经验法则:每组至少几百个转化样本

**Q3:A/B测试有哪些常见误区?**
- 过早停止测试:看到差异就停,可能只是随机波动
- 多重比较:测多个指标,总有一个"显著"
- 辛普森悖论:分组看有差异,合并看差异消失
