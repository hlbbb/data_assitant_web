## 1. 聚合函数 COUNT / SUM / AVG / MAX / MIN

一句话：聚合函数就是统计手段——数数、求和、求平均、找最大最小。

**生活比喻**：班上算总分、算平均分、数人数——这些就是聚合。一条 SQL 搞定，不用 Excel。

**语法**：

| 函数 | 作用 | 例子 |
|------|------|------|
| `COUNT(*)` | 统计所有行 | `COUNT(*)` |
| `COUNT(列)` | 统计该列非 NULL 的行数 | `COUNT(bonus)` |
| `SUM(列)` | 求和 | `SUM(salary)` |
| `AVG(列)` | 求平均（忽略 NULL） | `AVG(salary)` |
| `MAX(列)` | 最大值 | `MAX(salary)` |
| `MIN(列)` | 最小值 | `MIN(salary)` |

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `COUNT(*) AS 总数` | 给聚合结果起别名，结果清晰 |
| 不好的写法 | `COUNT(*)` | 不起别名，列名叫 COUNT(*)，谁看得懂？ |

**案例1（基础）**：

```sql
-- 统计员工总数、平均薪资、最高薪资、最低薪资
SELECT
    COUNT(*)    AS 员工总数,
    AVG(salary) AS 平均薪资,
    MAX(salary) AS 最高薪资,
    MIN(salary) AS 最低薪资
FROM employees;
```

**运行结果：**

```text
+----------+----------+----------+----------+
| 员工总数 | 平均薪资 | 最高薪资 | 最低薪资 |
+----------+----------+----------+----------+
|       12 | 13375.00 | 20000.00 |  8500.00 |
+----------+----------+----------+----------+
```

**案例2（进阶）**：

```sql
-- 计算奖金总额、有奖金人数、无奖金人数
-- COUNT(bonus) 只数非NULL的行
SELECT
    SUM(bonus)              AS 奖金总额,
    COUNT(bonus)            AS 有奖金人数,
    COUNT(*) - COUNT(bonus) AS 无奖金人数
FROM employees;
```

**运行结果：**

```text
+----------+----------+----------+
| 奖金总额 | 有奖金人数 | 无奖金人数 |
+----------+----------+----------+
| 27000.00 |        8 |        4 |
+----------+----------+----------+
```

**教学点 #1**：聚合函数就是统计。`COUNT(*)` 数行，`COUNT(列)` 数非 NULL 行，`SUM/AVG/MAX/MIN` 忽略 NULL。

### 📌 真实业务案例：销售日报统计

电商运营每天要看的数据，一条 SQL 搞定：

```sql
-- 场景：每天早上看的销售汇总（假设有 orders 订单表）
SELECT
    COUNT(*)                    AS 今日订单数,
    SUM(total_amount)           AS 今日销售额,
    AVG(total_amount)           AS 客单价,
    MAX(total_amount)           AS 最大单,
    MIN(total_amount)           AS 最小单,
    SUM(CASE WHEN pay_status = '已支付' THEN 1 ELSE 0 END) AS 已支付订单,
    SUM(CASE WHEN pay_status = '已支付' THEN total_amount ELSE 0 END) AS 实收金额
FROM orders
WHERE DATE(create_time) = CURDATE();
```

**这种写法好在哪？**
- 一条 SQL 出 7 个指标，不用写 7 次查询
- 用 `CASE WHEN` 做条件统计，灵活得很
- 运营一看就知道今天业绩怎么样

### ⚠️ 新手常见坑

**坑1：`COUNT(列)` vs `COUNT(*)` 分不清**
```sql
-- ❌ 想数总人数，结果少了
SELECT COUNT(bonus) FROM employees;  -- 只数有奖金的，8个人

-- ✅ 正确写法
SELECT COUNT(*) FROM employees;       -- 12个人
```
**教训**：数人头用 `COUNT(*)`，数"有某个字段的人"才用 `COUNT(列)`。

**坑2：`AVG` 遇 NULL 偏大，误导决策**
```sql
-- 人事部 2 个人奖金都是 NULL
SELECT department, AVG(bonus) FROM employees WHERE department = '人事部' GROUP BY department;
-- 结果：NULL（不是 0！）

-- 老板问"人均奖金多少"，你报 NULL？还是要解释半天？
-- ✅ 这样写才对
SELECT department, AVG(IFNULL(bonus, 0)) AS 人均奖金 FROM employees WHERE department = '人事部' GROUP BY department;
-- 结果：0.00，清晰明了
```
**教训**：做财务报表、KPI 报告时，`AVG` 一定要处理 NULL，不然数字偏大。

**坑3：聚合结果直接拿去算，忘了 NULL 的存在**
```sql
-- ❌ 危险！如果某部门奖金全是 NULL，SUM 返回 NULL
SELECT department, SUM(bonus) * 1.1 AS 明年预算 FROM employees GROUP BY department;
-- 人事部结果：NULL（不是 0！），乘以 1.1 还是 NULL

-- ✅ 安全写法
SELECT department, IFNULL(SUM(bonus), 0) * 1.1 AS 明年预算 FROM employees GROUP BY department;
```

### 🎯 面试高频题

**Q1：`COUNT(*)`、`COUNT(1)`、`COUNT(列)` 有什么区别？**
- **答案**：
  - `COUNT(*)` 和 `COUNT(1)` 效果一样，都是数所有行（MySQL 内部优化成一样）
  - `COUNT(列)` 只数该列非 NULL 的行
  - 性能上：`COUNT(*)` 和 `COUNT(1)` 在 InnoDB 中效率相同，都比 `COUNT(列)` 快一点（因为不用检查列值）

**Q2：为什么 `SUM(空结果集)` 返回 NULL 而不是 0？**
- **答案**：SQL 标准规定：聚合函数对空集操作，`COUNT` 返回 0，其他返回 NULL。这是"没有数据"和"数据是 0"的区别。
- **实际处理**：用 `IFNULL(SUM(col), 0)` 或 `COALESCE(SUM(col), 0)` 兜底。

**Q3：如何统计"有重复值的字段有多少种不同的值"？**
- **答案**：`COUNT(DISTINCT 列)`
```sql
SELECT COUNT(DISTINCT department) AS 部门数 FROM employees;  -- 结果：4
```

### 💡 什么时候用 / 什么时候别用

**✅ 该用聚合函数的场景：**
- 做 Dashboard、数据大屏（总销售额、总订单数、平均值）
- 财务报表（月度/季度汇总）
- 运营日报（今日新增用户、活跃用户）
- 性能监控（平均响应时间、最大并发数）

**❌ 不该用的场景：**
- 需要明细数据时（每个订单的具体商品，用 `SELECT *`，别聚合）
- 需要保留原始行时（聚合后行数变少，明细丢了）
- 做关联查询时（聚合后 ID 丢了，关联不上）

## 2. GROUP BY 分组聚合

一句话：先把数据分成几组，再对每组分别统计。

**生活比喻**：把衣服按颜色分到不同柜子——红色的一柜、蓝色的一柜，然后数每个柜子有几件。GROUP BY 就是"按颜色分柜子"。

**语法**：`SELECT 聚合列, 聚合函数 FROM 表 WHERE 条件 GROUP BY 分组列`

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | 先 WHERE 过滤，再 GROUP BY 分组 | 分组前先筛，效率高 |
| 不好的写法 | 先 GROUP BY，再靠 HAVING 过滤 | 能用 WHERE 过滤的别用 HAVING，性能差 |

**案例1（基础）**：

```sql
-- 按部门分组，统计每部门人数和平均薪资
SELECT
    department AS 部门,
    COUNT(*)   AS 人数,
    AVG(salary) AS 平均薪资
FROM employees
WHERE department IS NOT NULL
GROUP BY department;
```

**运行结果：**

```text
+------+------+----------+
| 部门 | 人数 | 平均薪资  |
+------+------+----------+
| 技术部 |    4 | 17250.00 |
| 市场部 |    3 | 12000.00 |
| 人事部 |    2 |  9750.00 |
| 财务部 |    2 | 13750.00 |
+------+------+----------+
```

**案例2（进阶）**：

```sql
-- 按部门分组，同时看每个部门的奖金状态
-- 用 CASE WHEN 把 NULL 标记为"无奖金"
SELECT
    department AS 部门,
    CASE WHEN bonus IS NULL THEN '无奖金' ELSE '有奖金' END AS 奖金状态,
    COUNT(*)   AS 人数
FROM employees
WHERE department IS NOT NULL
GROUP BY department, bonus IS NULL;
```

**运行结果：**

```text
+------+----------+------+
| 部门 | 奖金状态 | 人数  |
+------+----------+------+
| 技术部 | 有奖金   |    4 |
| 市场部 | 有奖金   |    3 |
| 人事部 | 无奖金   |    2 |
| 财务部 | 无奖金   |    1 |
| 财务部 | 有奖金   |    1 |
+------+----------+------+
```

**教学点 #2**：GROUP BY 是分组，像按颜色分柜子。SELECT 中的非聚合列必须出现在 GROUP BY 里，否则结果不确定。

### 📌 真实业务案例：用户活跃度分析

互联网产品最关心的指标——DAU（日活）、MAU（月活）、留存率，全靠 GROUP BY：

```sql
-- 场景：统计每个用户的月度活跃天数（假设有 user_logs 登录日志表）
SELECT
    user_id,
    COUNT(DISTINCT DATE(login_time)) AS 月活跃天数,
    MIN(DATE(login_time)) AS 首次登录日,
    MAX(DATE(login_time)) AS 最后登录日,
    CASE 
        WHEN COUNT(DISTINCT DATE(login_time)) >= 20 THEN '高活用户'
        WHEN COUNT(DISTINCT DATE(login_time)) >= 10 THEN '中活用户'
        ELSE '低活用户'
    END AS 用户等级
FROM user_logs
WHERE login_time >= '2024-01-01' AND login_time < '2024-02-01'
GROUP BY user_id
ORDER BY 月活跃天数 DESC;
```

**这种写法好在哪？**
- 一条 SQL 算出每个用户的活跃情况
- 用 `CASE WHEN` 做用户分层，运营直接拿去用
- `COUNT(DISTINCT DATE(...))` 去重统计，同一天登录多次只算 1 天

### 📌 真实业务案例：销售业绩排行榜

```sql
-- 场景：按销售员统计月度业绩，排出 TOP 10
SELECT
    salesperson_id,
    salesperson_name,
    COUNT(*) AS 订单数,
    SUM(order_amount) AS 销售总额,
    AVG(order_amount) AS 平均客单价,
    SUM(CASE WHEN order_status = '退货' THEN 1 ELSE 0 END) AS 退货单数,
    ROUND(SUM(CASE WHEN order_status = '退货' THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS 退货率
FROM orders
WHERE order_date >= '2024-01-01' AND order_date < '2024-02-01'
GROUP BY salesperson_id, salesperson_name
HAVING COUNT(*) >= 5  -- 至少 5 单才参与排名，避免样本太小
ORDER BY 销售总额 DESC
LIMIT 10;
```

**这种写法好在哪？**
- 多维度统计：订单数、销售额、客单价、退货率
- 用 HAVING 过滤掉样本太小的销售员（数据才有参考价值）
- 直接 ORDER BY + LIMIT 出 TOP 10，不用再写代码排序

---

### ⚠️ 新手常见坑

**坑1：SELECT 里写了非聚合列，GROUP BY 里没写——报错或结果乱**
```sql
-- ❌ 经典错误！MySQL 5.7+ 会报错，老版本返回不确定结果
SELECT department, name, AVG(salary) FROM employees GROUP BY department;
-- 错误信息：SELECT 列表中的 'name' 不在 GROUP BY 子句中...

-- 为什么会错？一个部门有多个人，name 选哪个？数据库不知道
-- ✅ 正确写法1：把 name 也加到 GROUP BY
SELECT department, name, AVG(salary) FROM employees GROUP BY department, name;

-- ✅ 正确写法2：只查聚合结果，不要 name
SELECT department, AVG(salary) FROM employees GROUP BY department;

-- ✅ 正确写法3：用聚合函数处理 name（比如取第一个）
SELECT department, ANY_VALUE(name) AS 代表员工, AVG(salary) FROM employees GROUP BY department;
```
**教训**：SELECT 里的非聚合列，必须出现在 GROUP BY 里，这是铁律。

**坑2：GROUP BY 后想用 WHERE 过滤聚合结果——语法报错**
```sql
-- ❌ 想筛选平均薪资 > 10000 的部门，写错了
SELECT department, AVG(salary) FROM employees WHERE AVG(salary) > 10000 GROUP BY department;
-- 报错：WHERE 子句不能使用聚合函数

-- ✅ 正确写法：用 HAVING
SELECT department, AVG(salary) FROM employees GROUP BY department HAVING AVG(salary) > 10000;
```
**教训**：WHERE 过滤原始行，HAVING 过滤分组后的结果。

**坑3：GROUP BY NULL 值——NULL 会被分到一组**
```sql
SELECT department, COUNT(*) FROM employees GROUP BY department;
-- 结果里会有一行：department = NULL, COUNT(*) = 1
-- NULL 被当成一个"组"了

-- ✅ 如果不想统计 NULL，先过滤
SELECT department, COUNT(*) FROM employees WHERE department IS NOT NULL GROUP BY department;
```
**教训**：GROUP BY 会把 NULL 当成一个组，不想统计 NULL 就先 WHERE 过掉。

**坑4：GROUP BY 多列时，顺序影响结果**
```sql
-- 这两个查询结果不同！
SELECT department, bonus, COUNT(*) FROM employees GROUP BY department, bonus;
SELECT bonus, department, COUNT(*) FROM employees GROUP BY bonus, department;
-- 分组逻辑一样，但结果展示顺序不同
```
**教训**：GROUP BY 多列时，顺序决定结果排序，想按特定顺序就加 ORDER BY。

---

### 🎯 面试高频题

**Q1：GROUP BY 和 DISTINCT 有什么区别？什么时候用哪个？**
- **答案**：
  - `DISTINCT` 只去重，不聚合
  - `GROUP BY` 可以去重 + 聚合（统计每组的数量、求和等）
  - 只需要去重：用 `DISTINCT`（语义更清晰）
  - 需要统计每组信息：用 `GROUP BY`

**Q2：GROUP BY 为什么比 DISTINCT 性能差？**
- **答案**：不一定！MySQL 优化器会把简单 `GROUP BY` 优化成 `DISTINCT`。但如果 GROUP BY 后面有聚合函数（SUM、COUNT 等），就必须走分组逻辑，性能会比纯 DISTINCT 差一点。

**Q3：如何实现"分组后取每组的前 N 条"？**
- **答案**：这是经典面试题，叫"分组 Top N"问题。MySQL 8.0+ 用窗口函数：
```sql
-- 取每个部门薪资最高的 2 个人
SELECT * FROM (
    SELECT 
        department, name, salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
) t WHERE rn <= 2;
```
MySQL 5.7 及以下版本需要用子查询或变量实现，比较麻烦。

---

### 💡 什么时候用 / 什么时候别用

**✅ 该用 GROUP BY 的场景：**
- 统计报表（按部门/地区/时间分组汇总）
- 用户分群（按行为特征分组）
- 数据分析（找规律、看分布）
- 去重统计（配合 COUNT DISTINCT）

**❌ 不该用的场景：**
- 只需要去重，不需要聚合（用 DISTINCT 更清晰）
- 需要保留所有明细行（GROUP BY 会压缩行）
- 分组字段太多（性能差，且结果难以理解）

## 3. HAVING 分组后过滤

一句话：分完组之后，再筛一遍。WHERE 筛行，HAVING 筛组。

**生活比喻**：按颜色分完柜子后，只留"件数超过 5 的柜子"。HAVING 就是分完组之后的二次筛选。

**语法**：`GROUP BY 分组列 HAVING 聚合条件`

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `HAVING COUNT(*) >= 2` | 对组设条件，语义明确 |
| 不好的写法 | `WHERE COUNT(*) >= 2` | WHERE 不能用聚合函数！语法直接报错 |

**案例1（基础）**：

```sql
-- 筛选平均薪资大于 13000 的部门
SELECT
    department  AS 部门,
    AVG(salary) AS 平均薪资
FROM employees
WHERE department IS NOT NULL
GROUP BY department
HAVING AVG(salary) > 13000;
```

**运行结果：**

```text
+------+----------+
| 部门 | 平均薪资  |
+------+----------+
| 技术部 | 17250.00 |
| 财务部 | 13750.00 |
+------+----------+
```

**案例2（进阶）**：

```sql
-- 筛选人数>=2 且平均薪资>12000 的部门
SELECT
    department  AS 部门,
    COUNT(*)    AS 人数,
    AVG(salary) AS 平均薪资
FROM employees
WHERE department IS NOT NULL
GROUP BY department
HAVING COUNT(*) >= 2 AND AVG(salary) > 12000;
```

**运行结果：**

```text
+------+------+----------+
| 部门 | 人数 | 平均薪资  |
+------+------+----------+
| 技术部 |    4 | 17250.00 |
| 财务部 |    2 | 13750.00 |
+------+------+----------+
```

**教学点 #3**：WHERE 筛行，HAVING 筛组。能用 WHERE 过滤的别用 HAVING，性能更好。

---

### 📌 真实业务案例：财务月报筛选

财务做月报，只看"有实际收入"的部门：

```sql
-- 场景：筛选月收入超过 10 万的部门，且排除测试部门
SELECT
    department AS 部门,
    COUNT(*) AS 有效订单数,
    SUM(amount) AS 月收入,
    AVG(amount) AS 平均订单金额
FROM finance_records
WHERE 
    record_month = '2024-01'
    AND department NOT LIKE '%测试%'  -- 用 WHERE 过滤，不是 HAVING
    AND status = '已确认'
GROUP BY department
HAVING SUM(amount) > 100000  -- 用 HAVING 过滤聚合结果
ORDER BY 月收入 DESC;
```

**这种写法好在哪？**
- WHERE 先过滤掉测试部门和未确认记录，减少分组数据量
- HAVING 再筛选收入达标的部门
- 性能比全用 HAVING 好很多

---

### ⚠️ 新手常见坑

**坑1：HAVING 和 WHERE 分不清，乱用**
```sql
-- ❌ 用 HAVING 过滤原始行，性能差
SELECT department, AVG(salary) 
FROM employees 
GROUP BY department 
HAVING department != '测试部';  -- department 不是聚合结果，应该用 WHERE

-- ✅ 正确写法：用 WHERE 过滤原始行
SELECT department, AVG(salary) 
FROM employees 
WHERE department != '测试部'
GROUP BY department;
```
**教训**：过滤原始行用 WHERE，过滤聚合结果用 HAVING。别混用。

**坑2：HAVING 里用别名——MySQL 可以，其他数据库报错**
```sql
-- MySQL 里这样写能跑
SELECT department, AVG(salary) AS avg_sal 
FROM employees 
GROUP BY department 
HAVING avg_sal > 10000;  -- 用了别名

-- 但 Oracle、SQL Server 会报错！
-- ✅ 兼容写法：用原表达式
SELECT department, AVG(salary) AS avg_sal 
FROM employees 
GROUP BY department 
HAVING AVG(salary) > 10000;  -- 用原表达式，不依赖别名
```
**教训**：写 SQL 要考虑数据库兼容性，别依赖 MySQL 的"宽容"。

**坑3：HAVING 里写非聚合条件——逻辑错误**
```sql
-- ❌ 想筛选"技术部且平均薪资 > 10000"，写错了
SELECT department, AVG(salary) 
FROM employees 
GROUP BY department 
HAVING department = '技术部' AND AVG(salary) > 10000;
-- 能跑，但性能差！department 应该用 WHERE 过滤

-- ✅ 正确写法
SELECT department, AVG(salary) 
FROM employees 
WHERE department = '技术部'
GROUP BY department 
HAVING AVG(salary) > 10000;
```
**教训**：HAVING 只用于聚合条件，非聚合条件放 WHERE。

**坑4：HAVING 和 ORDER BY 混淆**
```sql
-- ❌ 想按平均薪资排序，写成了 HAVING
SELECT department, AVG(salary) 
FROM employees 
GROUP BY department 
HAVING AVG(salary) > 10000
ORDER BY AVG(salary) DESC;  -- 这是排序，不是过滤

-- ✅ 正确理解：HAVING 是过滤，ORDER BY 是排序
```

---

### 🎯 面试高频题

**Q1：WHERE 和 HAVING 的执行顺序是什么？**
- **答案**：执行顺序是：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
- **理解**：WHERE 先过滤原始数据，GROUP BY 再分组，HAVING 最后过滤分组结果。

**Q2：为什么 HAVING 不能替代 WHERE？**
- **答案**：
  1. **性能**：WHERE 在分组前过滤，减少数据量；HAVING 在分组后过滤，浪费计算
  2. **语义**：WHERE 过滤行，HAVING 过滤组，语义不同
  3. **功能**：WHERE 不能用聚合函数，HAVING 可以

**Q3：以下 SQL 有什么问题？**
```sql
SELECT department, COUNT(*) AS cnt
FROM employees
HAVING cnt > 2;
```
- **答案**：没有 GROUP BY，HAVING 没意义。这相当于对全表过滤，但 cnt 是聚合结果，没有分组就没有意义。
- **修正**：要么加 GROUP BY，要么去掉 HAVING。

---

### 💡 什么时候用 / 什么时候别用

**✅ 该用 HAVING 的场景：**
- 过滤聚合结果（如：筛选平均薪资 > 10000 的部门）
- 过滤分组统计值（如：筛选订单数 > 10 的用户）
- 多条件组合过滤（如：人数 >= 5 且平均薪资 > 10000）

**❌ 不该用的场景：**
- 过滤原始行（用 WHERE，性能更好）
- 没有聚合函数时（用 WHERE）
- 只需要排序时（用 ORDER BY）

**性能优化口诀**：
> 能用 WHERE 先过滤，别等 HAVING 再筛。
> WHERE 减数据量，HAVING 减结果集。
> 先筛再分组，性能翻倍好。

## 4. 聚合函数与 NULL 的交互

一句话：聚合函数遇到 NULL 会"跳过"，但 `COUNT(*)` 例外——它数的是行，NULL 也算一行。

**生活比喻**：数教室里的人数——有人在但没交作业（NULL），人还在（COUNT(*) 算），但作业份数不算他的（COUNT(作业) 不算）。

**语法**：理解规则比记语法重要：
- `COUNT(*)` 数所有行，NULL 也算
- `COUNT(列)` 跳过 NULL
- `SUM / AVG / MAX / MIN` 跳过 NULL
- 全是 NULL 时，`SUM` 返回 NULL，`COUNT` 返回 0
- `AVG` 只对非 NULL 值求平均，可能导致结果偏大

**好的写法 vs 不好的写法**：

| | 写法 | 说明 |
|---|---|---|
| 好的写法 | `AVG(IFNULL(bonus, 0))` | NULL 当 0 处理，结果准确 |
| 不好的写法 | `AVG(bonus)` | NULL 被跳过，平均值偏大 |

**案例1（基础）**：

```sql
-- 对比 COUNT(*) 与 COUNT(bonus) 的区别
SELECT
    COUNT(*)               AS 总行数,
    COUNT(bonus)           AS 非NULL奖金行数,
    COUNT(*) - COUNT(bonus) AS NULL行数
FROM employees;
```

**运行结果：**

```text
+--------+--------------+--------+
| 总行数 | 非NULL奖金行数 | NULL行数 |
+--------+--------------+--------+
|     12 |            8 |      4 |
+--------+--------------+--------+
```

**案例2（进阶）**：

```sql
-- 按部门对比：AVG 忽略 NULL vs 用 IFNULL 修正
-- 忽略NULL的 AVG 偏高，用 IFNULL 修正后更准确
SELECT
    department              AS 部门,
    AVG(bonus)             AS 原始平均奖金_忽略NULL,
    AVG(IFNULL(bonus, 0))  AS 修正平均奖金_NULL当0,
    SUM(bonus)             AS 奖金总额
FROM employees
WHERE department IS NOT NULL
GROUP BY department;
```

**运行结果：**

```text
+------+------------------+------------------+----------+
| 部门 | 原始平均奖金_忽略NULL | 修正平均奖金_NULL当0 | 奖金总额  |
+------+------------------+------------------+----------+
| 技术部 |       5000.00 |       5000.00 | 20000.00 |
| 市场部 |       1500.00 |       1500.00 |  4500.00 |
| 人事部 |         NULL   |          0.00 |     NULL |
| 财务部 |       2500.00 |       1250.00 |  2500.00 |
+------+------------------+------------------+----------+
```

**教学点 #4**：聚合函数跳过 NULL，`COUNT(*)` 除外。`AVG` 遇 NULL 会偏高，用 `IFNULL` 修正。

---

### 📌 真实业务案例：财务报表 NULL 处理

财务做年终奖金报表，NULL 值处理不当会被老板质疑：

```sql
-- 场景：统计各部门奖金情况，NULL 必须显示为"未发放"
SELECT
    department AS 部门,
    COUNT(*) AS 总人数,
    COUNT(bonus) AS 已发奖金人数,
    COUNT(*) - COUNT(bonus) AS 未发奖金人数,
    IFNULL(SUM(bonus), 0) AS 奖金总额,
    ROUND(IFNULL(AVG(bonus), 0), 2) AS 人均奖金_原始,
    ROUND(AVG(IFNULL(bonus, 0)), 2) AS 人均奖金_修正,
    CASE 
        WHEN COUNT(bonus) = 0 THEN '全员未发放'
        WHEN COUNT(bonus) < COUNT(*) THEN '部分未发放'
        ELSE '全员已发放'
    END AS 发放状态
FROM employees
WHERE department IS NOT NULL
GROUP BY department;
```

**这种写法好在哪？**
- `IFNULL(SUM(bonus), 0)` 兜底，避免 NULL 出现在报表
- `AVG(IFNULL(bonus, 0))` 把未发放的当 0，算出真实人均
- 用 `CASE WHEN` 给发放状态打标签，报表更直观

---

### 📌 真实业务案例：电商订单金额统计

电商统计 GMV（成交总额），退款订单金额为 NULL：

```sql
-- 场景：统计每日 GMV，退款的订单金额要算进去（当 0 处理）
SELECT
    DATE(order_time) AS 日期,
    COUNT(*) AS 订单总数,
    COUNT(final_amount) AS 有效订单数,
    COUNT(*) - COUNT(final_amount) AS 退款订单数,
    IFNULL(SUM(final_amount), 0) AS GMV,
    ROUND(IFNULL(AVG(final_amount), 0), 2) AS 平均客单价,
    ROUND(SUM(final_amount) / COUNT(*), 2) AS 真实客单价_含退款
FROM orders
WHERE order_time >= '2024-01-01' AND order_time < '2024-02-01'
GROUP BY DATE(order_time);
```

**注意**：
- `AVG(final_amount)` 会忽略 NULL，算的是"有效订单的平均"
- `SUM(final_amount) / COUNT(*)` 把退款订单当 0，算的是"所有订单的平均"
- 报表里要写清楚是哪种口径，不然老板会问为什么数字不一样

### ⚠️ 新手常见坑

**坑1：SUM 全是 NULL 返回 NULL，不是 0**
```sql
-- 人事部奖金全是 NULL
SELECT department, SUM(bonus) AS 奖金总额 FROM employees WHERE department = '人事部' GROUP BY department;
-- 结果：NULL（不是 0！）

-- ✅ 兜底写法
SELECT department, IFNULL(SUM(bonus), 0) AS 奖金总额 FROM employees WHERE department = '人事部' GROUP BY department;
-- 结果：0.00
```
**教训**：聚合结果可能返回 NULL，报表展示前一定要用 IFNULL 或 COALESCE 兜底。

**坑2：AVG 忽略 NULL，导致平均值偏高**
```sql
-- 部门有 3 人，奖金分别是 1000、2000、NULL
-- AVG(bonus) = (1000 + 2000) / 2 = 1500（除以 2，忽略 NULL）
-- 但真实应该是 (1000 + 2000 + 0) / 3 = 1000（除以 3）

-- ✅ 修正写法
SELECT AVG(IFNULL(bonus, 0)) AS 真实平均奖金 FROM employees WHERE department = '某部门';
```
**教训**：做财务报表、KPI 计算时，一定要搞清楚 NULL 要不要当 0，不然数字差很多。

**坑3：COUNT 空集返回 0，其他聚合返回 NULL**
```sql
-- 空表
SELECT COUNT(*) FROM empty_table;      -- 结果：0
SELECT SUM(amount) FROM empty_table;   -- 结果：NULL
SELECT AVG(amount) FROM empty_table;   -- 结果：NULL
SELECT MAX(amount) FROM empty_table;   -- 结果：NULL
```
**教训**：COUNT 特殊，返回 0；其他聚合函数对空集返回 NULL。代码里要处理 NULL 情况。

**坑4：IFNULL vs COALESCE vs NULLIF 分不清**
```sql
-- IFNULL(col, 0)：如果是 NULL，返回 0（MySQL 特有）
-- COALESCE(col, 0)：如果是 NULL，返回 0（标准 SQL，兼容所有数据库）
-- NULLIF(col, 0)：如果 col = 0，返回 NULL（反向操作）

-- ✅ 推荐用 COALESCE（兼容性更好）
SELECT COALESCE(SUM(bonus), 0) AS 奖金总额 FROM employees GROUP BY department;
```

### 🎯 面试高频题

**Q1：AVG 忽略 NULL，怎么处理？有什么业务场景需要注意？**
- **答案**：
  - 用 `AVG(IFNULL(col, 0))` 或 `AVG(COALESCE(col, 0))` 把 NULL 当 0
  - 业务场景：计算人均奖金、人均消费时，未参与的人要算进去，不然数据偏高

**Q2：COUNT(*)、COUNT(1)、COUNT(col) 性能有什么区别？**
- **答案**：
  - MySQL 优化器会把 `COUNT(*)` 和 `COUNT(1)` 优化成一样
  - `COUNT(col)` 需要检查列是否为 NULL，稍微慢一点
  - InnoDB 引擎下，三者性能差异不大（除非 col 有索引）

**Q3：如何统计"某字段为 NULL 的行数"？**
- **答案**：
```sql
-- 方法1：COUNT(*) - COUNT(col)
SELECT COUNT(*) - COUNT(bonus) AS NULL行数 FROM employees;

-- 方法2：SUM(CASE WHEN)
SELECT SUM(CASE WHEN bonus IS NULL THEN 1 ELSE 0 END) AS NULL行数 FROM employees;

-- 方法3：COUNT(CASE WHEN)
SELECT COUNT(CASE WHEN bonus IS NULL THEN 1 END) AS NULL行数 FROM employees;
```

**Q4：GROUP BY 后，SELECT 里能出现哪些列？**
- **答案**：
  - 出现在 GROUP BY 里的列
  - 聚合函数（COUNT、SUM、AVG、MAX、MIN）
  - 其他列不能直接出现（MySQL 老版本允许，但结果不确定；新版本报错）

---

### 💡 什么时候用 / 什么时候别用

**✅ 该用 NULL 处理函数的场景：**
- 财务报表（金额不能为 NULL，要显示 0）
- KPI 指标（平均值要算未参与的人）
- 数据展示（NULL 显示为"未填写"、"暂无"）

**✅ 该保留 NULL 的场景：**
- 数据分析时，NULL 代表"缺失"，有意义
- 统计覆盖率时，NULL 和 0 是两回事
- 需要区分"值为 0"和"值未知"时

**性能建议**：
- IFNULL 和 COALESCE 性能差异极小，选哪个都行
- 大量 NULL 值会影响索引效率，设计表时要考虑默认值
- 统计时用 COUNT(col) 会跳过 NULL，比 COUNT(*) 稍慢

## 第二阶段总结速查表

| 知识点 | 核心语法 | 一句话要点 | 常见坑 |
|--------|----------|-----------|--------|
| 聚合函数 | `COUNT/SUM/AVG/MAX/MIN` | 统计手段，`COUNT(*)` 数行，`COUNT(列)` 数非 NULL | `AVG` 遇 NULL 偏高，用 `IFNULL` 修正 |
| GROUP BY | `GROUP BY 列` | 按颜色分柜子，SELECT 非聚合列必须出现在 GROUP BY | NULL 会被分到一组，不想统计先 WHERE 过掉 |
| HAVING | `HAVING 条件` | 分完组再筛，能用 WHERE 别用 HAVING | 过滤原始行用 WHERE，过滤聚合结果用 HAVING |
| NULL 与聚合 | `IFNULL / COALESCE` | 聚合跳 NULL，`AVG` 遇 NULL 偏高需修正 | `SUM` 空集返回 NULL，不是 0 |

---

## 🎯 实战场景速查

| 业务场景 | SQL 模板 | 关键点 |
|---------|---------|--------|
| 销售日报 | `COUNT(*) + SUM(amount) + AVG(amount)` | 用 `CASE WHEN` 做条件统计 |
| 用户活跃度 | `COUNT(DISTINCT DATE(login_time))` | 去重统计，同一天多次登录只算 1 次 |
| 业绩排行榜 | `GROUP BY + HAVING + ORDER BY + LIMIT` | 用 HAVING 过滤样本太小的数据 |
| 财务报表 | `IFNULL(SUM(amount), 0)` | NULL 必须兜底，避免报表出现 NULL |
| 分组 Top N | `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` | MySQL 8.0+ 用窗口函数 |

## 📝 面试必背题

1. **COUNT(*) vs COUNT(1) vs COUNT(列)**：前两者等价，后者只数非 NULL
2. **WHERE vs HAVING**：WHERE 过滤行，HAVING 过滤组；WHERE 先执行
3. **AVG 忽略 NULL 怎么办**：用 `AVG(IFNULL(col, 0))` 或 `AVG(COALESCE(col, 0))`
4. **GROUP BY NULL 值**：NULL 会被分到一组，不想统计先 WHERE 过掉
5. **分组 Top N**：MySQL 8.0+ 用 `ROW_NUMBER()`，老版本用子查询

## ⚡ 性能优化口诀

```
能用 WHERE 先过滤，别等 HAVING 再筛。
WHERE 减数据量，HAVING 减结果集。
先筛再分组，性能翻倍好。
COUNT(*) 数行快，COUNT(列) 要检查 NULL。
聚合结果可能 NULL，IFNULL 兜底保平安。
```

## 🔧 调试技巧

**遇到聚合结果不对时，按这个顺序检查：**

1. **检查 NULL**：`SELECT COUNT(*), COUNT(col) FROM table` 看看有多少 NULL
2. **检查分组**：`SELECT 分组列, COUNT(*) FROM table GROUP BY 分组列` 看看分组是否正确
3. **检查过滤**：先去掉 HAVING，看看原始分组结果
4. **检查逻辑**：`AVG` 是不是忽略了 NULL？`SUM` 空集是不是返回 NULL？
5. **检查数据**：用 `SELECT * FROM table LIMIT 10` 看看原始数据长什么样
